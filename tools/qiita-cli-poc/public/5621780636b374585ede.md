## 0. まず結論を先に(3 行 + 図 1 枚)

- 筋骨格のヒトを歩かせようとして、自分で書いた**進化探索(evolutionary search)**が「生存 8 秒・前進 0.68 m」という良い点数を出した。**足と頭で測り直したら、体は 0.21 秒で傾き切り、0.40 秒で頭が床の近くまで落ちていた。**
- なぜ点数が良かったのか。**転倒の判定が「腰の高さが 0.55 m を割ったか」の 1 条件しか無かった**からだ。頭から突っ込んだまま腰だけが前へ運ばれれば、この判定はいつまでも「生きている」と答える。
- 嘘を見破ったのは派手なスコアではなく、**足と頭という別の尺度**だった。この検証バーは他の実験にも転用できる。以降は、その検証バーで自分の実験を片っ端から測り直した記録である。

![同じ 1 回の試行を 2 つの尺度で測ると結論が逆になることを示した図。左は探索が最大化していた量(生存 8 秒・腰の前進 +0.46 m)、右は足と頭が示した実体(立位を保てたのは 0.21 秒、頭は 0.40 秒で床の近くへ、歩行判定は DID NOT WALK)](https://raw.githubusercontent.com/furuse-kazufumi/fullsense/main/docs/articles/assets/hillco_walk/fig01_score_vs_reality.svg)

この記事は、その 1 つの失敗から始まって、**借り物の体で本物の歩行を見に行き、その安定が「松葉杖」だったと突き止め、足そのものを設計し直し、最後に「見る道具」を研究インフラとして作る**までの記録だ。うまくいっていない部分は、うまくいっていないまま書く。

## 1. 用語集(先に言葉だけ)

| 用語 | かみくだき |
|---|---|
| 筋骨格モデル(musculoskeletal model) | 骨と関節だけでなく、**筋肉 1 本 1 本**を持たせた人体モデル。関節を直接回すのではなく、筋が縮む力で動く |
| モーションキャプチャ(motion capture, mocap) | 人間の動きをセンサーで記録したデータ。ここでは「熟練者の歩行のお手本」 |
| キネマティック再生(kinematic replay) | 記録した姿勢を順に表示するだけの**アニメーション**。物理を解いていない。見た目は派手 |
| 模倣学習(imitation learning) | お手本の動きを真似させて方策(policy)を作る学習 |
| 行動クローン(Behavioral Cloning, BC) | 「この状態ではこの動き」を教師あり回帰で丸暗記させる、最も単純な模倣 |
| 進化探索(evolutionary search) | 多数の候補をランダムに試し、良かったものを残して少しずつ改良する最適化。勾配を使わない |
| 強化学習(Reinforcement Learning, RL) | 報酬を最大化する方策を試行錯誤で学ぶ |
| 適合度(fitness) | 進化探索が最大化しようとする点数。**この式の書き方が、そのまま結果の質になる** |
| 報酬ハッキング(reward hacking) | 課題を解かずに、点数の抜け道だけを突いて高得点を取ること |
| 足軌道(foot trajectory) | 足そのものが空間をどう動いたか。歩行の真偽を判定する一次証拠 |
| 反位相(anti-phase) | 左右の足が逆のタイミングで上下すること。歩行の特徴 |
| 遊脚(swing) / 支持脚(stance) | 宙に浮いて前へ運ばれる側の脚 / 体重を支えている側の脚 |

| 全身制御(Whole-Body Control, WBC) | 全身の関節・接触力をまとめて 1 つの最適化問題として解く制御 |
| 参照状態初期化(Reference State Initialisation, RSI) | 学習中、転ぶたびにお手本の途中の姿勢から再開させる手法。訓練の点数が実力以上に良く見える原因になる |
| 受動剛性(passive stiffness) | 筋や腱が「何もしなくても」持っている、関節を元に戻そうとする硬さ |

## 2. かみくだき(やさしい順に 3 段)

**第 1 段 — たとえ話で。**
マラソンの記録を「ゴールテープを切った時刻」だけで測るとする。ところが選手が転んで、転んだ勢いのまま体が前へ滑ってテープを切ったとしたら。時計は立派な記録を出すが、それは走ったことにならない。今回起きたのは、これとほぼ同じだ。私のプログラムは「腰の高さ」だけを見て生死を判定していたので、**頭から突っ込んだ姿勢のまま腰が運ばれていく状態を、8 秒間ずっと「生きている」と答え続けた**。

**第 2 段 — もう少し具体的に。**
コンピュータの中の人体に歩き方を探させるとき、「良い歩き方とは何か」を数式で書いて渡す。私が書いた式は 3 つの項からできていた。**倒れずにいた時間**、**腰がどれだけ前に進んだか**、**足をどれだけ持ち上げたか**。一見よさそうに見える。だが「倒れずにいた」の定義が腰の高さ 1 つだけで、しかも足上げの項は左右の足の**小さい方**を見るだけで、**左右が交互かどうかを一度も問わない**。だから「両足を同時にバタつかせながら頭から突っ込む」動きでも、点数は伸びる。

**第 3 段 — 技術的に。**
適合度は `surv + 3.0*fwd + 5.0*min(both_lift, 0.05)` で、`surv` の終了条件は骨盤 z < 0.55 m の 1 条件、`fwd` は骨盤 x の変位、`both_lift` は `min(max_lift_L, max_lift_R)` を 5 cm で飽和させたもの。時刻に関する制約が無いため、位相構造(交互性)は評価に入らない。実際に得られた最良個体を順運動学と接触計算で 1 コマずつ検証すると、体幹の傾きは 0.21 秒で 2.85 rad に達し、頭の高さは 0.40 秒で 0.243 m まで落ちる。それでも骨盤 z の最小値は 0.656 m で、終了条件には最後まで触れない。足を基準にした前進は +0.18 m、骨盤基準では +0.46 m。この差が、そのまま「倒れ込みを前進と数えていた分」である。

## 3. 舞台設定 — 前章までに立っていた場所

この連載では、自宅の PC で人体や動物のモデルを動かして、その結果を正直に記録している。今回の話に入る前に、直前の 3 本で分かっていたことを短くまとめておく。

| 前章 | 分かったこと | 残った宿題 |
|---|---|---|
| 骨と筋だけの人体を、自宅の CPU で立たせ・掴ませ・飲ませ・踊らせた | 700 本の筋を持つ人体モデル(evis)は、**立てた・掴めた・飲めた**。派手な運動の動画の多くは mocap の再生であって物理ではない、という線引きも決めた | **歩けていない** |
| 重心を下げたら類人猿ロボは歩き、坂を登り、下りた。だが「筋肉」では歩けなかった | **トルクで直接関節を回す**類人猿型なら歩き、坂を登り、下りた | 同じ課題を**筋で駆動**すると、歩けない |
| 2.24 m の「勝ち」は、実は滑っていた | 歩行の報酬を敵対的に監査したら、勝ちは小さくなったが正直になった。滑走・同期バウンド・手や胴での支えという抜け道を塞いだ | 監査したのは**トルク駆動の四足/類人猿型**。人体の筋骨格ではまだやっていない |

つまり私は、「トルクなら歩けるが、筋では歩けない」「人体モデルは立てるが歩けない」という 2 つの壁の前にいた。そして**報酬の抜け道は、前章で一度痛い目を見ている**。にもかかわらず、今回また同じ穴に落ちた。落ち方が前回と違ったので、そこから書く。

## 第0幕 — そもそも、自前の筋骨格ヒトは1歩も歩けなかった

役割をはっきりさせておく。私はコードをほとんど書かない。方向を決め、動画を目で見て、数字と絵の食い違いを疑い、続けるか止めるかを決める。実装と実験を回しているのは相棒の AI である。この記事に並ぶ失敗は、私の判断ミスと AI の測り方のミスが混ざっている。どちらの失敗かは、そのつど主語で書き分ける。

### 0-1. かみくだき — 糸のゆるんだ操り人形、という当時の見立て

この研究の主人公は、骨と筋だけでできた人体のシミュレーションだ。骨が 132 本、筋が 700 本。関節を「モーターで回す」のではなく、筋が縮む力で骨を引っぱって動かす。イメージは**操り人形**が近い。ただし、ふつうの操り人形は糸を放せば関節がぶらぶらするだけだが、本物の人体の関節には靭帯があり、力を抜いていても「そこそこの硬さ」——**受動剛性(passive stiffness)**——が残る。座ったまま急に眠っても、首や膝がゼロ抵抗で折れたりはしない。

当時の私たちは、そのモデルに硬さが入っていないと見ていた。糸(筋)を張っていない関節が全身の半分以上あり、力を抜いた瞬間に全部同時にゆるむ、と。**歩き方を教える以前に、立たせられなかった** —— 第0幕はその話であり、同時に「その診断自体が後で撤回された」話でもある。

体は自作ではない。公開されている筋骨格モデル **MS-Human-700**(Zuo et al., ICRA 2024、Apache-2.0)で、プロジェクト内では **evis** と呼んでいる。MuJoCo にロードして測った実数値は、**自由度 nq=85 / アクチュエータ nu=700 / 腱 700 / body 81 / site 2856 / 全身質量 60.22 kg**。「700筋」は宣伝文句ではなく実数だ。

### 0-2. 全滅の記録

「歩かせよう」として実際に走らせた試行のうち、**歩行に関しては成功と書けるものが一つもない。**

| 何を試したか | 結果(実測) |
|---|---|
| 100筋変種の歩行。6構成 × 複数シード | **全 run で歩数 0**。デューティ比 = **1.00** = 足が一度も地面から離れなかった |
| 直立の総当り10通り(解析 CoP 則5変種 / GRU シナジー / 整定始点 / 静止カリキュラム 他) | **天井 4.6 / 8秒・held-out 0/8**。制御クラス・行動空間・特徴量・目的関数・初期条件・最適化器の6軸を変えても破れない |
| 700筋の直接学習(中枢パターン生成器 CPG の追従)。生 700 次元の筋活性をゼロから探索 | **報酬 −6144 に崩壊、前進速度 nan**(ランダムな共収縮で発散) |
| 運動シナジー行動空間へ(32×700 の非負値行列因子分解の基底) | **前進速度が有限に = 発散は解消**。しかし決定論的な方策は **0.2 秒(16 step)で崩壊**。学習中の評価報酬は確率的平均で汚染されていた |
| フィードフォワード(重力補償シナジー) | 残差 38% 削減止まり。開ループ適用では **0.36〜0.39 秒で崩壊** |

ただし、この「頑健な負け」を**歩行以外にまで広げて書くのは正しくない**。同じ時期、100筋変種 + PPO(26,633 パラメータ)は決定論再生で **8.00 / 8 秒・held-out 8/8**、訓練ホライズンを 15 秒へ伸ばした版は **8 / 10 / 12 / 14 秒すべて held-out 8/8** を通している(ただし平地限定で、2°の斜面では 0/8)。**立位は取れている。取れていないのは歩行であり、また 700 筋での直立である。** 都合の悪い成功も、同じ重みで残す。

そして最も痛い一行がこれだ。

> **cpg2 〜 cpg9 の全 RL は、膝が逆向きに曲がる参照歩容で学習していた = 公正なテストではなかった**

お手本データを別モデルから移すとき(リターゲティング, retargeting)、関節角の符号の規約を無視してコピーしていた。移し元は膝の屈曲が負、evis は正。符号が真逆だったので evis の膝は **−1.08 rad(= 62°)の過伸展**、逆関節の方向へ駆動されていた。膝角の相関は **−1.000**(完全な鏡像)、可動域違反 **388 / 7900 フレーム**。修正後は相関 **+1.000**、違反 22 件(すべて 0.0002 rad = 数値ノイズ)。

> **持ち帰り①**: お手本を別の体へ移すとき、**宣言された関節軸を信用しない**。実際に関節を微小に動かし、親フレームでどちら向きの回転が誘起されるかを測ってから符号を決める。この確認を飛ばすと、8世代分の学習実験がまるごと無効になる。

### 0-3. 当時の真因診断: ふにゃふにゃの操り人形(のちに撤回)

AI は長いあいだ**報酬と最適化器を疑って**いた。報酬の重みを振り、探索ノイズを変え、シナジー基底を作り直し、CPG のクロックを足し、warm-start を試す。全部やって全部負けた。

決定打はモデル側の受動特性を測ったときに出た。**700筋モデルは、85 関節のうち 50 が受動剛性ゼロ**。筋の活性をすべて 0 にして落としたときの生存は、受動剛性 0 で **0.19 s**、50 で 1.02 s、100 で 3.26 s、**300 で 30 s(直立を維持)**。制御を1行も書かずに、剛性を足すだけで 0.19 秒が 30 秒になる。「崩壊の主因は制御ではなく身体だ」—— ここで一度、結論を出した。

**この結論は、二重に訂正することになる。**

**訂正(1): 測定器の起点が浮いていた。** 診断の起点にしていた初期姿勢が、**床から +2.11cm 浮いていて接触点 0**、しかも膝の等式拘束とも不整合だった。上の数字は**すべて 2cm 落下の衝撃込み**である。接地させ、拘束を整合させて同じゼロ活性・剛性0 を測り直すと **0.518 秒**だった。数字の向きは変わらないが、絶対値は上書きされている。

**訂正(2): 「操り人形」という診断そのものが誤りだった。** 接地・拘束整合させた本物の立位で測り直すと、**700筋モデルは平均活性 2.8%・飽和した筋 1 本だけで完全な静的平衡を張っていた**(内部37関節の残差 0.008 N·m)。**evis は平衡を持たない操り人形ではない。** 関節 PD をどう足しても、筋をバイパスして理想トルクを直接与えても 10 秒立たない(最良 3.43 秒)ことから、欠けていたのは剛性でも筋力でもフィードフォワードでもなく、**圧力中心(Center of Pressure, CoP)の制御**だった —— というのが現在の理解である。

一次資料の側が自己訂正したので、記事の側も撤回する。「剛性 300 で 30 秒立つ」も、落ち着いた平衡姿勢にバネで留めているだけのほぼ自明な結果で、後述の torque-twin には転移しなかった。剛性は診断の道具としては決定的だったが、解決策ではない。代替案の「拮抗筋を同時に縮めて(共収縮)硬さを作る」も負けている。零空間を解いて正味トルクを中立化する正しい実装にすると、**正味トルクは 219.0 → 0.1 N·m と完璧に中立化されたのに、生存は 0.22 秒で一定**。膝の実効剛性は **−16.94 N·m/rad** と**負**(曲がるほど曲げる方向に力が出る)だった。共収縮は膝安定化の正しい道具ではない、というのがこの実験の確定情報である。

### 0-4. 診断②: そもそも動かせない関節に報酬を出していた

もう一つの発見は、**駆動系そのものの不足**だった。借り物のモデル(LocoMuJoCo HumanoidMuscle, 92筋)で最も劇的に出ている。報酬整形・参照・クロック・探索・warm-start・トレッドミル・腕固めと **11通りの実験がすべて歩行不成立**、どれも「脚だけで 2 秒立つ」に収束した。私が「上半身は動いているのか? 全身で重心バランスを取っているのか?」と聞いたのがきっかけで調べたら、真因はこれだった。

> **このモデルは腕に駆動筋が1本もない**(モーメントアーム ——筋が関節を回すときのテコの長さ—— が 0)。ロールアウト中、腕は受動的に 60° 暴れる死重になっていた。

歩行は全身の角運動量を管理する運動なので、腕が受動的に振り回されている限り**原理的に不可能**だった。数十時間の GPU 実験は、**静的なチェック1回**(モーメントアーム ≠ 0 の筋を数えるだけ)で回避できたはずだ。

同種の事故は他にもある。100筋変種は、制御器を外して静的平衡が成立するかを非負最小二乗で判定すると、保持できる横オフセットが **4.9cm(残差 3.2%)まで**。片足立ちに必要なのは **9.8cm** で、約2倍足りない。**片足立ちが構造的に不可能な体**に、片足支持を要求する報酬を出していたことになる(700筋なら 10.3cm で残差 2.4% = 成立する)。別トラックの低重心二足では、**20 本の Hill 型筋モデルを全開で駆動しても足が 0.002m しか動かなかった** —— 関節のゼロ位置が力-長さ曲線の裾の外にあったのだ。

> **持ち帰り②(この幕の中心)**: **報酬を弄る前に、その体がそもそも要求を満たす駆動系を持っているか確認する。** 手順は3つで、いずれも数分で終わる。①**モーメントアームを数える**(0 なら、その関節への報酬は永遠に届かない)②**静的平衡を解く**(制御器を外し、目標姿勢が静力学的に成立するかを最小二乗で判定。成立しないなら制御でなく機体の課題)③**零点(null)を測る**(何も制御しないときの生存時間。それを超えない結果は「できた」ではなく「倒れる途中」)。


### 0-5. GPU の壁 —— 700筋は XLA でコンパイルが通らない

機体の問題が分かって「700筋でやるしかない」と決めた直後、計算基盤に阻まれた。MuJoCo を GPU 上で並列に回す **MJX(MuJoCo XLA)** は物理計算をコンパイラ **XLA** のグラフに変換するが、700 筋 / 740 腱 / 2856 site の evis ではそのグラフが巨大になりすぎた。既定のアロケータでは内部チェックに引っかかって落ち、切り替えると落ちない代わりに **GPU 使用率 51% でも 40 分で 5M step に届かない ≒ 約 2000 steps/s** —— **当時の CPU 実行より遅い**(比較対象は同じ体を CPU で回したときの実測値。並列環境数が違うので、付録 B に載せた GPU 学習の steps/s とは絶対値を比較できない)。グラフサイズは約 28GB で、**並列環境数を 512 から 64 に落としてもメモリ不足**。調整でどうにかなる遅さではなく、XLA 側の限界だった。

ここで私が出した案が転換点になった —— **「筋を使わず、関節角度と力だけで動かしてみては」**。こうして作ったのが **torque-twin(トルク駆動の双子)** だ。700 の筋と 700 の腱を削除し、独立関節 49 個にモーターを付ける。**変わったのは駆動系だけで、アクチュエータ 700 → 49、腱 700 → 0、GPU メモリ 11 GB → 4.5 GB。** 内訳は **脚 14 + 脊椎/首 21 + 腕/手首 14**。

ここは正確に書き分けておく。torque-twin の自由度は nq = nv = **97** だが、**この +12 DoF は torque-twin 化で増えたのではない**。腰椎の分節化(L1〜L5 が関節なしで溶接され、前弯が各セグメントの姿勢に焼き込まれていたのを、4 関節 × 3 軸で開いた)という**別工程**で、筋モデルのまま 85 → 97 になっている。

そして重要なのは、**ギア比が推測ではなく実測**であることだ。参照歩容の各姿勢で全筋を最大活性化し、各筋の力とモーメントアームから「その関節まわりに筋が実際に出せる最大トルク」を求め、その最大値をギアにしている。実測値は股関節屈曲 274.0 / 288.3、足首 240.6 / 238.2、膝 204.0 / 204.7、距骨下関節 48.9 / 48.8、足趾 5.0、肘 17.5 N·m(左/右)、全 49 モーターで最小 5.0 / 中央値 87.2 / 最大 340.2 N·m。

**torque-twin は本物の筋を超える力を出せない。** これは「筋モデルが重いから諦めてロボットにした」のではなく、**筋の力学的な出力上限を保ったまま、計算だけを軽くする切り分け**である。扱える形で先に歩行を実証し、その後で筋へ蒸留する、という順番を意図している。

### 0-6. torque-twin の代償

初回の学習は **0.06 秒で終了**した。転倒ですらない(重心高さは 0.975 のまま)。初期のランダムな方策が生理学的な最大トルクを 1 step で叩き込み、軽い遠位関節 —— **右足首が 143 rad/s** —— で速度が暴走し、健全性チェック(|関節速度| > 100 rad/s)に引っかかったのだ。**筋が持っていた活性化ダイナミクスと力速度関係(force-velocity relationship)を、モーターは持っていない。** AI は当初これを「ギア比 1.0 の設定ミス」と誤診しており、訂正済みである。

対策は私が出した見立てをそのまま実装したものだ ——「可動域と同じように、各自由度は速度の範囲も持つはずだ。荷重を支える関節ほど速度制限は厳しい」。Hill 型筋の力速度上限を入れる(各サブステップで短縮方向のトルクに `clip(1 − w/wmax, 0, 1)` を掛ける)と、エピソード長は step 0 の時点で **6 → 37**、生存率は **0.67 → 0.97** になった。**サブステップごとに掛けることが必須**で、制御ステップごとでは効かないことを CPU で実証している。

計測側の致命的なバグも2件出ている。ひとつは**重心速度の API が常に 0 を返していた**こと —— MuJoCo の `subtree_linvel` は MJX の forward / step では計算されない。重心速度を使う前進報酬が常に定数になり、**前進方向の勾配がゼロ**だった。もうひとつは**時間軸の不整合**で、物理刻み 0.002 秒で回していたが (a) 数値安定の限界は 0.001 秒、(b) 参照歩容は 100Hz、(c) 制御周期は別、とバラバラだった。結果、step-0 で **0.05 秒で即死**。自由落下でも 0.186 秒かかるので、物理が数値的に爆発していたということだ。

> **持ち帰り③**: 学習が進まないとき、**報酬より先に「時間軸の比」と「メトリクスが本当に計算されているか」を疑う**。物理刻み : 制御周期 : 参照データの周期 : 実時間 の4つの比を、実験前に紙に書いて確認する。**黙って 0 を返す API** は、エラーを出さないぶん報酬バグより発見が遅れる。

第0幕の結論は単純だ。**自前の筋骨格ヒトは、この時点で1歩も歩いていない。** 次の幕は、その体の上に「歩容クロック」を1枚重ねて探索したら、**歩けたように見えるスコア**が出てしまった話である。

## 第1幕 — 「歩けた」と思った探索が、頭から突っ込んでいた

### 1-1. 第1幕の舞台 — 手元にあった立位制御器

手元にあったのは「**しゃがんだ姿勢なら外乱に耐えて10秒立てる**」制御器だけだった。母集団探索(population search)で見つけた6個の数字の組で、姿勢の PD 制御に重心(Center of Mass, COM)フィードバックを足しただけのものだ(比例ゲイン 65.255 / 微分ゲイン 0.5 / 重心の前後ずれ→足首 380.022 / 同→股関節屈曲 399.147 / 重心の左右ずれ→股関節内転 −20.306 / 初期の足首前傾 0.197 rad)。

この立位制御器を**固定したまま**、上に「歩容クロック(gait clock)」を1枚重ねる。位相が周期 $T$ で回り、前半は左足が支持脚、後半は右足が支持脚。クロックがやることは2つだけ —— **(a) 横方向の重心目標を、いま支持している側の足へ寄せる**、**(b) 支持していない側の脚を、半周期のあいだ $\sin$ の山形で股関節屈曲 + 膝屈曲だけ持ち上げ、また下ろす**。

探索する変数はたった5個だ。歩行周期(0.4〜1.4 秒)、横方向の体重移動量(0.0〜1.2)、遊脚の股関節屈曲量(0.0〜1.2 rad)、遊脚の膝屈曲量(−1.2〜0.2 rad)、そして重心目標を前へずらす量 = 前進のための「前のめり」(−0.10〜0.10 m)。実行設定は **8世代 × 個体300 / 1個体あたり3シード / 1ロールアウト8秒 / 物理刻み 0.002秒**(上位何個体を残したかはログに残っていない = **未記録**)。延べ 7,200 ロールアウト = **16時間分の物理**を、CPU の MuJoCo だけで回したことになる。

### 1-2. 適合度関数(fitness)の全文 — 抜け穴はここに埋まっていた

探索が最大化していた量は、次の10行がすべてだ。

```python
def fitness(self, gp, secs=6.0, seeds=3, vfwd=0.0):
    R = [self.rollout(gp, secs, seed=s, vfwd=vfwd) for s in range(seeds)]
    surv      = np.mean([r["surv"] for r in R])                     # 生存時間(秒)
    both_lift = np.mean([min(r["lift_r"], r["lift_l"]) for r in R]) # 両足とも「上がった」量
    fwd       = np.mean([r["fwd"] for r in R])                      # 前進量(m)
    if vfwd > 0.0:   # 前進モード: 移動を報酬。ただし「立っている」「足が上がる」で門をかける
        f = surv + 3.0 * fwd + 5.0 * min(both_lift, 0.05)
    else:            # その場モード: 転ばずに交互ステップ
        f = surv + 30.0 * min(both_lift, 0.06)
    return f, float(surv), float(both_lift), float(fwd)
```

この docstring にはこう書いてある ——「**適合度は正直(HONEST)である: 立っていること、かつ両足を本当に交互に(alternately)上げることを要求する。引きずりや片足シャッフルは低い点しか取れない**」。

穴を塞いだつもりでいて、塞げていたのは一部だけだった。探索が最高点を付けた個体(第2〜6世代、`best_fit=9.667`)の得点を項ごとに割ると、それが数字で見える。

| 項 | 式 | 実測値 | 得点 | 割合 |
|---|---|---:|---:|---:|
| 生存 | `surv` | 7.38 s | 7.38 | **76.3 %** |
| 前進 | `3.0 × fwd` | +0.68 m | 2.04 | 21.1 % |
| 両足挙上 | `5.0 × min(both_lift, 0.05)` | 8.5 cm → 5cm で頭打ち | 0.25 | **2.6 %** |
| 合計 | | | **9.67** | |

**足を上げることの配点が 2.6% しかない探索に、「歩け」と命じていた。** 残り 97% は「転ばずに、前へ出ろ」である。3項それぞれに独立した抜け穴があった。

**抜け穴①: 「生存」の定義が骨盤の高さ1条件だけ。** 打ち切り条件は「骨盤の高さ < 0.55 m」の一行だけだ(立位はおよそ 0.94 m)。骨盤が 55cm より高い位置にありさえすれば、**頭が床に着いていようが体幹が真っ二つに折れていようが「生存」**である。

**抜け穴②: 「前進」の定義が骨盤の前後位置。** 倒れ込めば骨盤は前に出る。

**抜け穴③: 「両足挙上」が時刻を見ていない。** `min(左足の最大挙上, 右足の最大挙上)` —— 左右それぞれの**ロールアウト全体での最大値**を取って、小さい方を採る。つまり **「左足が8秒間のどこかで5cm上がり、右足も8秒間のどこかで5cm上がる」だけで満点**になる。両足が同時に上がっても、跳ね上がっても区別できない。**docstring が自負した「交互に(alternately)」は、コードのどこにも書かれていなかった。** 意図はコメントにあり、要求はコードにない —— この食い違いが、そのまま次節の結果になる。

さらに `min(both_lift, 0.05)` の飽和が効く。**5cm を超えて足を上げても1点も増えない**ので、探索は 5cm ちょうどを確保して残りを前進に振る。実際ログでは、世代が進むにつれて両足挙上が 11.0cm → 19.2cm → **8.5cm** と下がりながら、前進が +0.12m → +0.35m → **+0.68m** へ伸びている。**探索は「歩く」から遠ざかりながら点数を上げていた。**

> **持ち帰り①**: 適合度は合計値でなく**項ごとの寄与率**で見る。「意図した性質」の配点が数%なら、それは要求ではなく飾りである。
> **持ち帰り②**: `min(x, cap)` の飽和項は、cap を超えた瞬間に無報酬になる。探索は必ず cap ぎりぎりを選ぶ。
> **持ち帰り③**: 時系列を `max` や `min` で1個のスカラーに畳んだ指標は、**タイミングの条件(交互・順序・持続)を一切表現できない**。docstring に書いた条件は、コードが評価していなければ存在しないのと同じである。

### 1-3. なぜ「重心の前進量」が嘘をつくのか — 倒立振子で説明する

人体を、足を床に固定した1本の棒(倒立振子, inverted pendulum)とみなす。棒が鉛直から角度 $\theta$ だけ前へ傾いたとき、重心の水平移動と両足の中点(support centre)の水平移動はこうなる。

$$
\Delta c_x = h\sin\theta \;(\neq 0),
\qquad
\Delta s_x = \tfrac{1}{2}\bigl(\Delta x_{\text{右足}} + \Delta x_{\text{左足}}\bigr) = 0
$$

この骨格の立位重心高さは $h \approx 0.97$ m(初期姿勢での実測 0.9749 m)。代入すると、**一歩も踏まずに 30° 倒れるだけで重心は約 0.49 m、45° なら約 0.69 m 前進する**。後者は、この探索が誇っていた前進量 +0.68 m とほぼ同じである。

つまり **重心や骨盤を進捗の物差しにした瞬間、「倒れること」が最も安上がりな得点源になる**。しかも倒れれば生存の項を失うはずだが、抜け穴①のせいで骨盤さえ高ければ生存扱いになるので、**倒れる代わりに「上半身だけ折る」**という、さらに安い解が残っていた。探索はそれを見つけた。

![足を床に固定したまま角度θ傾くと、足の中点は 1 mm も動かないのに重心だけが h·sinθ 前へ動くことを示した対比図](https://raw.githubusercontent.com/furuse-kazufumi/fullsense/main/docs/articles/assets/hillco_walk/fig04_inverted_pendulum.svg)

対策は「**残っている体でなく、地面に対する足の入れ替えだけを進捗と認める**」に尽きる。後の実験で入れた足基準の前進速度は、両足中点の変位を差分するだけの数行だ。

```python
# 足基準前進: 両足中点(support centre)の前進速度。倒れても重心は前に出るが
# 足は運ばれないので、前傾ダイブ/転倒は前進と評価されない。
sc  = 0.5 * (data.xpos[calcn_r] + data.xpos[calcn_l])
sc0 = 0.5 * (prev.xpos[calcn_r] + prev.xpos[calcn_l])
vx  = (sc[0] - sc0[0]) / dt
```

ダイブは重心が前進し足中点は不変なので 0 点、歩行は両方が前進するので満点。定義を1個変えるだけで、**この**ズルの経路は閉じる。**ただし別の抜け道までは塞げていない** —— 後の監査で、両足を床につけたまま滑らせる走法と、片足だけを宙に振る動きという2つの穴が見つかる(第7幕)。

### 1-5. 訂正 —— 既存の公開版に書いた数字自体が、再現しなかった

honest disclosure として、いちばん重い話を書く。この連載の既存公開版には、この artifact をこう書いていた。

> 腰の高さが立位 0.94m からそのまま床の転倒ライン 0.55m まで沈み、**1.15秒で転倒** / 前進どころか **23cm後方** へ / **両足が69%の時間、宙に浮いている**

**現存するチャンピオンのファイルからは、この3つの数値がどれも出ない。** 今日測ると、骨盤は 0.656 m までしか下がらず(沈まない)、骨盤は **+46.0cm 前進**しており(後退でない)、両足浮きは **0.19** である。

なぜ食い違ったのか。**コードから確実に言えることが2つある。**

**(a) 保存されるのは「最後の世代のチャンピオン」だけ。**

```
[gen 2..6] best_fit=9.667 surv=7.38s both_lift=8.5cm  fwd=+0.68m
[gen 7]    best_fit=9.864 surv=8.00s both_lift=20.3cm fwd=+0.54m
[done] saved 4000 frames (8.0s) -> ..._best_qpos.npy
```

**記事が掲げた「+0.68m」の個体は第7世代で更新されており、そのロールアウトはそもそも保存されていない。** 保存されたのは前進 +0.54m・足上げ 20.3cm の別個体だ。**探索が最高点を付けた個体と、保存・再生された個体は別物**である。**(b) スコアと保存軌跡は、同じ個体でも一致しない設計だった。** 適合度は初期姿勢に微小ノイズを入れた3シードの平均、保存する再生はノイズ無しの決定論的な1本。**同じパラメータでも数字は一致しない。**

したがって初稿の 1.15秒 / −23cm / 69% は「当時、別のファイルを検証した結果で、その後の実行で保存先が上書きされた」可能性が高いと考えている —— ただし**これは推測であり、確認できていない**。**結論そのものは、今日の再検証でも変わらない。** 頭が床上24cm、0.21秒で体幹が折れ、遊脚は2cm、足は 0.18m しか進んでいない —— これは歩行ではない。**しかし、結論が生き残っても数値は差し替える。** 「嘘の報告をしない・実測だけで語る」という取り決めは、実務ではこういう地味な作業のことを指している。

> **持ち帰り⑤**: **artifact を摘発した数字にも来歴(provenance)が要る。** 敗因は、検証器の出力を標準出力に流して捨て、入力ファイルも上書きを許していたこと。**検証結果は「入力ファイル + 出力ログ + 図」を1組で残す**。これをやっていれば、初稿の数値は今日3秒で照合できた。

## 幕間 — 嘘を見破る道具の作り方(転用可能)

上の摘発に使った検証器そのものを、転用できる形で開示する。全体で190行、依存は MuJoCo と NumPy だけだ。

**原則1: 派生量でなく一次量を見る。接地は「高さの閾値」でなく物理エンジンの接触計算で判定する。** 足が地面に着いているかを `if foot_z < 0.02` のような閾値で判定してはいけない。理由は3つ。**閾値はモデル依存**(箱足と解剖学的な足では基準高さが違う)、**報酬側と仮定を共有してしまう**(報酬も高さ閾値で接地を判定していると、検証器と報酬が同じ穴に同時に落ちる)、**改ざんできてしまう**(制御器は関節角を自由に選べるので、閾値の側で「接地して見える姿勢」を作れる)。対して MuJoCo の `mj_forward` はその姿勢での**実際の衝突検出**を走らせて接触点の配列を埋める。床と足のペアが立っているかどうかは、**制御器から手の届かない量**だ。

**原則2: 学習ループの中の数値でなく、保存した軌跡を後から独立に再生する。** 関節角の記録を1コマずつ書き込み、速度をゼロにして `mj_forward` を呼ぶ。純粋な順運動学 + 衝突計算になり、学習時の環境設定・報酬・正規化・乱数から切り離された経路で同じ姿勢を再評価できる。**原則3: 進捗は足で測る。 原則4: 判定を1つの数に畳まない。合格文言もぼかさない。**

```python
"""記録した qpos を1コマずつ物理エンジンに通し、足そのものに問う検証器。
   接地判定は高さ閾値でなく MuJoCo の衝突ソルバが出す実接触点 = 改ざん不能。"""
import numpy as np, mujoco

def foot_floor_contact(m, d, floor_gids, foot_gids):
    """この足の「床との」実接触数と、最も食い込んでいる接触の距離。"""
    n, mind = 0, 1e9
    for i in range(d.ncon):
        c = d.contact[i]
        on_floor = (c.geom1 in floor_gids) or (c.geom2 in floor_gids)
        on_foot  = (c.geom1 in foot_gids)  or (c.geom2 in foot_gids)
        if on_floor and on_foot:
            n += 1
            mind = min(mind, float(c.dist))
    return n, (mind if n else np.nan)

# --- 記録した qpos を1コマずつ再生(qvel=0 の純キネマティクス+衝突) ---
for t in range(T):
    d.qpos[:] = q[t]; d.qvel[:] = 0.0
    mujoco.mj_forward(m, d)                        # ← ここで d.contact が埋まる
    pelz[t] = d.xpos[pel, 2]
    zl[t], zr[t] = d.xpos[cl, 2], d.xpos[cr, 2]    # 足の高さ
    conL[t] = foot_floor_contact(m, d, floor, padL)[0] > 0
    conR[t] = foot_floor_contact(m, d, floor, padR)[0] > 0

# --- 判定(全部 raw な足の量だけで決まる) ---
alt      = len(swL) >= 1 and len(swR) >= 1        # 左右が交互に遊脚になったか
clear_ok = all(z[a:b].max() - f > 0.03 for ...)   # 遊脚は3cm以上浮いたか
max_slip = max(abs(x[b-1] - x[a]) for 支持区間)   # 支持足が滑っていないか
fell     = np.where(pelz < FALL_Z)[0]             # 腰は沈まなかったか(FALL_Z=0.55)
if alt and clear_ok and not len(fell) and max_slip < 0.05:
    print("PLAUSIBLE genuine stepping (alternating swings, real clearance, planted stance).")
```

これを以下**足軌道の検証バー**(自前モデル用)と呼ぶ。判定は4条件だけだ。**(1) 左右が交互に遊脚になるか**(各足の遊脚区間が1回以上。0.05秒以下は雑音として捨てる)、**(2) 遊脚が本当に浮くか**(立位基準高さから > 0.03 m。今回の擦り足 1.5〜2.0cm はここで落ちる)、**(3) 支持足が滑っていないか**(0.1秒以上の支持区間で前後変位 < 0.05 m。スケート型の抜け道を塞ぐ)、**(4) 腰が維持されるか**(骨盤 > 0.55 m。※本章の教訓により、これ**だけ**では不十分)。補助指標として接地率・両足支持・両足浮きの割合を必ず表示する。今回の artifact なら「両足支持 0.44・両足浮き 0.19」の時点で、まともな歩容でないことが読める。合格しても最後は `PLAUSIBLE genuine stepping ... Confirm visually.` —— **合格文言ですら「目で見て確認せよ」で終わる**。「たぶん大丈夫」と書ける検証器は、いずれ「たぶん」の側に倒れる。

姿勢側の第二検証器は、本章の教訓から追加した。前進は**両足中点**で測り、骨盤高さ・頭の高さ・体幹の傾き・横倒れの4点で転倒を判定する。閾値はすべて実測に紐づけてあり、どの値をどう決めたか(とくに頭のキルライン)は第7幕で書く。

## 第2幕 — 黒箱をやめて、明示的な制御へ

ここまでの実験は、ほぼすべてが**強化学習(Reinforcement Learning, RL)**だった。報酬を設計し、GPU で数千万ステップ回し、出てきた方策を検証する。そして繰り返し同じ壁にぶつかっていた ——「数値は良いのに、動画を見ると転んでいる」。

方針を変えたのは私の一言だった ——「**RL は万能でない。位置決めのピラミッドサーチのように、複数の動作候補を追跡すべき**」。同じ日にもう一つ出した指示が、この二幕全体の設計方針になっている ——「**end-to-end の RL を減らし、明示制御を骨格に、RL は狭い補正に**」。**明示制御(explicit control)** とは、方策をニューラルネットに学習させるのではなく、「重心をここへ戻す」「この関節をこの角度へ」といった**数式で書き下した制御則**のことだ。中身が読めるので、失敗したときに「どの式のどの項が効かなかったのか」を追える。黒箱の RL には無い性質である。

このとき「そもそも仕組みが正しいか真剣に調べては」とも言った。検証させたところ、**モデル自体は健全**だった(受動状態で発散せず、骨盤 0.95→0.14 m と穏やかに崩落、最大の関節速度は 13 rad/s)。ただし立位は限界的で、重心が踵より **7.8 cm 前方**にあった。問題は「仕組み」ではなく「アプローチ」で、AI は end-to-end RL にゼロから立位を発見させようとしていた —— 私が示した戦略に真っ向から反することを、気づかずにやっていたわけだ。

### 2-1. 消去法の梯子

QP に至ったのは「最適化を使ってみたかったから」ではない。**下から順に潰して、残ったのが QP だった**。

| 段 | 手法 | 結果(実測) |
|---|---|---|
| 0 | 何もしない(零点)= 開ループで立位姿勢を保持 | **~1.4 s で転倒** |
| 1 | 受動剛性 = 全関節にバネを入れて靭帯の代わりに | 700筋 evis で剛性100→3.3 s、300→30 s(※起点が床から 2.11cm 浮いた状態での旧測定。接地させ直した活性ゼロ・剛性0 は **0.518 s**。第0幕の訂正節を参照)。**しかも torque-twin には転移しなかった** |
| 2 | 重力補償 + 姿勢 PD + キャプチャポイント | **~1.4 s**(目標 10 s) |
| 3 | 仮想モデル制御(VMC)= 重心に「仮想の手」で力を加え、重心ヤコビアンで全関節に配分 | **~2 s で頭打ち** |
| 4 | 全身 QP | 第3幕 |

段 3 のコードのコメントが、行き詰まりの理由を一文で書いている。

> Per-joint PD + capture-point capped at ~2s because the pelvis is a non-actuated floating base: no single joint can hold it up; the legs must COOPERATE.
> (関節ごとの PD とキャプチャポイントは約2秒で頭打ちになった。骨盤が非駆動の浮遊ベースだからだ。どの単独関節もそれを支えられない。脚が**協調**しなければならない)

積分器を変えても、減衰を増やしても同じだった。**PD / 重力補償 / キャプチャポイント / VMC / 陰的積分器 / 受動剛性 / 減衰増 —— 明示制御の全手法が立位 2 秒未満**、重心ドリフトは 1〜2 m。正直に書くと、**この段階での「成果」は零点(1.4 秒)を最大でも 0.6 秒しか超えていない**。「2 秒立てた」は、勝ちではない。

### 2-2. 飽和ジレンマ —— 矛盾を見つけた瞬間

なぜ全部 2 秒で止まるのか。真因は、教科書には「ゲイン調整の話」として書かれがちだが、この体では構造的な**矛盾**として現れた。**改善したい特性**は姿勢の復元力(倒れかけを引き戻す速さ)、**悪化する特性**は必要トルクが上限(gear)を超えて**飽和**し、指令が嘘になること。

重要なのは、**両者が同じノブで繋がっている**ことだ。ゲインを上げれば復元力は増えるが飽和する。下げれば飽和しないが倒れる。実際、静的に保持するだけの重力補償なら飽和は起きない —— **飽和はゲインの問題ではなく、「復元力を出す」という要求そのものに埋まっている**。

ここで発想を変えた。従来の制御は「トルクを計算し、上限で切り捨てる(clip する)」。つまり**飽和は事故として起きる**。指令したトルクと実際に出るトルクが違ってしまい、その瞬間に制御則の前提が崩れる。だったら、**飽和を事故にせず、最初から制約として禁止すればいい**。「出せるトルクの範囲の中で、一番マシな動きを毎ステップ選ぶ」—— これは制御則ではなく**最適化問題**の形をしている。PD は「こう動け」と命令するが、体がその命令を実行できるかを知らない。二次計画法はそれを知っている。

> Because the torque ceiling is a hard constraint, the QP never asks for impossible torque -> no saturation blow-up.
> (トルク上限が**ハード制約**なので、QP は不可能なトルクを要求しない。だから飽和による崩壊が起きない)

> **持ち帰り⑦**: 「上限で clip している量」がある制御は、その clip が効いた瞬間に前提が壊れている。**clip を制約に格上げできないか**を疑うと、制御則が最適化問題に化けることがある。逆に言えば、**clip が一度でも効いたら、それは定式化のバグを知らせるサイン**として使える。

## 第3幕 — 全身QP(Whole-Body Control) — 立位は解けた、歩行は接触で壊れた

**二次計画法(Quadratic Programming, QP)** は「たくさんの制約を全部守りつつ、二乗誤差の合計を最小にする解」を一発で求める数理最適化で、制約が線形・目的が二次なら大域最適解が確実に出る。**全身制御(Whole-Body Control, WBC)** は関節を個別に制御せず、全関節と全接触点を**同時に**配分する制御で、二足歩行ロボットの標準手法だ。

対象は torque-twin。**一般化座標 97 / モータ 49 / 非駆動自由度 48 / 体重 60.22 kg / 物理刻み 0.002 s / トルク上限 最小 5.0・中央値 87.2・最大 340.2 N·m。** ここで効いてくるのが **非駆動自由度 48** である。骨盤は宙に浮いている **浮遊ベース(floating base)** で、そこにモータは付いていない。体を起こす力は、**足が地面を押した反作用としてしか**手に入らない。

### 3-1. 定式化 —— 何を決め、何を守るのか

毎制御ステップ、次の最適化を解く。決定変数は

$$
x = \begin{bmatrix} \ddot{q} \\ f_c \\ f_{eq} \end{bmatrix} \in \mathbb{R}^{n_v + 3n_c + n_e},
\qquad n_v = 97,\; n_e = 42
$$

で、$\ddot{q}$ は全関節加速度(骨盤 6 自由度を含む)、$f_c$ は接触点ごとの接触力(世界座標系の3成分)、$f_{eq}$ は膝の連成拘束などの反力である。ここが教科書的な QP-WBC と違う点: **トルク $\tau$ を決定変数に入れていない。** 運動方程式から $\tau$ を消去し、加速度と力だけを解く。変数が 49 本減り、トルク上限は「加速度と接触力の線形不等式」として書き直される。

コストは二乗誤差タスクの重み付き和で、**重心を支持基底へ**($w_{com}\|J_{com}\ddot{q} - a^*_{com}\|^2$、既定 $w_{com}=10.0$)、**姿勢を参照へ**($w_{post}\|\ddot{q}[\text{act}] - a^*_{post}\|^2$、既定 0.2)、それに冗長性を解く正則化が乗る。重心の目標加速度はキャプチャポイント風の比例微分レギュレータ $a^*_{com,xy} = -k_{p,c}(c_{xy} - s_{xy}) - k_{d,c}\dot{c}_{xy}$ で、両踵の中点 $s$ に向かって引く($k_{p,c}=30,\ k_{d,c}=8$)。重心速度は $\dot c = J_{com}\dot q$ で自前計算している —— 第0幕の「重心速度の API が黙って 0 を返す」問題があるためだ。制約が本題である。

制約は 5 本ある。括弧内の行数は、実際に解いている問題の大きさ。

**① 非駆動自由度の運動方程式**(等式・48 行)

$$\bigl[M\ddot{q} + h - B_c f_c - J_{eq}^\top f_{eq}\bigr]_{\text{unact}} = 0$$

骨盤と膝の連成にはモータが無い。**その行のトルクはゼロでなければならない。**

**② 接触点は加速しない**(等式・$3n_c$ 行)

$$J_c\ddot{q} = 0$$

接地した足は、地面を突き抜けも跳ねもしない。

**③ 連成拘束の維持**(等式・42 行)

$$J_{eq}\ddot{q} = 0$$

膝の連成など、モデル側が持っている等式拘束。

**④ トルク上限**(不等式・98 行) —— **これが飽和禁止の正体**

$$-g_a \le \bigl[M\ddot{q} + h - B_c f_c - J_{eq}^\top f_{eq}\bigr]_a \le g_a$$

前の幕まで、復元力を上げるとトルクが上限に張り付いて制御が壊れていた。
ここでは**上限そのものを制約として書いてある**ので、上限を超える解は最初から候補に入らない。

**⑤ 摩擦錐**(不等式・線形化・$5n_c$ 行)

$$-f_{z,i} \le 0, \quad \pm f_{x,i} - \mu f_{z,i} \le 0, \quad \pm f_{y,i} - \mu f_{z,i} \le 0$$

足は地面を引っ張れないし、摩擦を超える横向きの力も出せない($\mu = 0.9$)。


$M$ は完全慣性行列、$h$ は重力+コリオリ項、$B_c = J_c^\top$。制約 5 は正確な二次錐ではなく**ピラミッド近似**にしてある —— そのおかげで問題は二次計画のまま保たれ、高速なソルバが使える。解が出たらトルクを逆算し、ギアで割って正規化入力に直す。制約 4 を満たしていれば、この最終段の `clip` は原理的に効かない。**効いたら QP の前提が壊れている**というセルフチェックが埋め込まれている形だ。そして解が出なかったときは、**重力補償だけ**に落ちる。

```python
x = solve_qp(P, qv, G, hh, A, b, solver="osqp")
if x is None:
    qp_fail += 1                       # ← 「制御が消えた回数」のカウンタ
    for a in range(m.nu):
        d.ctrl[a] = np.clip(float(h[act_dof[a]]) / (gear[a] or 1.0), -1.0, 1.0)
```

この `qp_fail` という1変数が、以降の診断の主役になる。ソルバは立位・参照追従が osqp(ADMM 系の一次法)、自前歩容生成が clarabel(内点法・Rust 実装)。計算コストの**上界**は、5 秒ぶんのロールアウト(2500 制御ステップ)を壁時計 29.8 秒で回した記録から **約 11.9 ms/step(実時間比 約 6 倍遅)** —— ただしこれはプロセス起動とモデルコンパイル込みの上界で、**QP solve 単体の計測は未実施**である。

### 3-4. 接触が足りないなら、足せばいい —— 解剖学的な足裏パッド

CoP が消えるのが原因なら、**接触点を増やせばいい**。ここでも設計は私の一言から来ている ——「足裏は、かかとと母趾球の肉厚のパッドで、土踏まずは浮いている」。実装は、実行時に平底のボックス形状を足に追加するだけだ。

```python
PLANTAR_PADS = [
    ("heel", -0.060, 0.042, 0.042),   # 踵脂肪体、幅広(~8.4 x 8.4 cm)= 主荷重域
    ("ball",  0.078, 0.034, 0.048),   # 中足骨頭 / 母趾球 (~6.8 x 9.6 cm)
]
g.type    = mujoco.mjtGeom.mjGEOM_BOX
g.density = 0.0                       # ★質量ゼロ = 慣性を変えず接触幾何だけを足す
g.solref  = np.array([soft, 1.0])     # 柔軟接触 = 肉と皮膚の潰れ
```

設計上の決定が3つあり、どれも「ズルとの切り分け」に効いている。**(1) 質量ゼロ** —— 慣性も体重も変えず、接触幾何だけを足す。「足を大きくして安定させただけでは?」という疑いに、**そもそも重さが増えていない**と答えられる。**(2) 平底のボックス(球ではない)** —— 接触が点でなく面(4隅)になる。モデルの形状数は 361 → 365(2パッド × 2足)で、これが前節で消えた CoP 権限の回復にあたる。※接地時の接触点が実際に何点まで増えるかは、**本日の再実測では再現できなかった(未計測)**。**(3) 土踏まずはわざと非接地** —— 解剖学的に正しい足跡になる。

効果は実測されている: **崩落 1.4 s → 3.4 s**。さらに幅の最適化で、**幅広の踵(8.4 cm)にすると後方ドリフトが 2.4 m → 0.7 m** に減った(比較元の踵幅はコードに書かれていない)。母趾球は約 9.6 cm(解剖学的な実寸 ~10 cm 近傍)でドリフト最小。**幅広の踵が支配的な安定化要素**という結果は、人間の踵が足裏で最大の荷重面積を持つことと一致する。「解剖学的に正しくしたら性能が上がった」の、数少ない定量例だ。

### 3-5. 自家撞着 —— 一度も発火しないトリガ

> 🔭 **[この体が動くところを、任意の視点で見る（本命 evis ・全身QP）](https://furuse-kazufumi.github.io/fullsense/articles/assets/hillco_walk/walk_series_viewer.html?series=evisQP)**
> 横に倒れていく過程が見える。正面から見ると、前後ではなく左右に崩れていることが分かる。


接触点を増やしたので、次は自前で歩容を作る番だ。設計意図は明快だった ——「参照を追わない。直立姿勢を保ち(支持足は平らなまま = 接触点が多い = QP が解ける)、歩容位相に駆動される3つの QP タスクで**自分で**一歩を作る」。前節の実行不能を、接触点を保つことで回避する。ここまでは正しい。問題は**そのあと**にあった。

```python
# (A) 両足支持中の横重心目標 = 「左右の足の真ん中」に固定
base_xy = np.array(sup_xy) if swinging else 0.5 * (foot_nom[cal_l] + foot_nom[cal_r])

# (B) 踏み替えトリガ = 「重心が支持足に寄ったら」
shift_thr = shift_frac * abs(float(foot_nom[cal_l][1]))
on_sup = abs(com[1] - float(foot_nom[cur_sup][1])) < shift_thr
if (on_sup and t_phase > ds_min) or t_phase > ds_max:
    step_phase = "swing"; t_phase = 0.0
```

**この2つは同じ量について正反対のことを要求している。** 幾何で書くと1行で終わる。スタンス半幅を $w$、踏み替え閾値の係数を $\alpha$ とすると、両足支持相の制御目標は $c_y \to 0$(正中線)、トリガ条件は $|c_y - (\pm w)| < \alpha w$。制御が目標に到達した定常状態 $c_y = 0$ では左辺が $w$ になるので、条件は $w < \alpha w \iff \alpha > 1$ となる。

数値で確かめると、スタンス半幅は **$w = 0.0839$ m**、既定 $\alpha = 0.6$ の閾値は **0.0503 m**。目標偏差 0.0839 m は常にこれを上回るので、**定常状態では原理的に発火しない**。そしてこれまでのパラメータ探索が試した値は 0.35 / 0.4 / 0.45 / 0.5 / 0.55 / 0.6 の6通りで、**全部 1 未満**だった。

**つまり全 run を通じて、このトリガは構造的に一度も真になっていない。** 数十 run ぶんのパラメータ探索が、発火しないトリガの周りを回っていた。踏み出しは常に、もう一方の条件(既定 0.8 秒のタイムアウト)でしか起きない。設計意図だった「体重を支持足に乗せてから足を上げる」は実行されず、**体重が真ん中にあるまま反対の足を上げていた**。人間が絶対にしない動作である。横倒れが止まらないのも当然だった。


しかもコード自身が、この近傍で「気づきかけていた」痕跡を残している —— コメントには「緊急踏み出しのトリガは、**中心にいる開始時に発火してしまうのを避けるため**ここでは省いた」とある。**開始時に発火しないことを心配していたのに、一度も発火しないことには気づいていない。**

閾値がおかしいなら閾値を直せばいい —— そう考えて A/B を取った。

| | A: 係数 0.6(既定・発火不能) | B: 係数 1.5(発火可能) |
|---|---|---|
| 生存 | **3.34 s** / 5 s | **2.17 s** / 5 s |
| 前後ドリフト | −0.98 m | +0.08 m |
| qp_fail | 0 | 0 |
| **両足浮き** | **0.351** | **0.570**(悪化) |
| 片足支持 | 0.410 | 0.243 |

**トリガを発火可能にしただけでは悪化した。** 解釈(**これは仮説と明示する**): 係数 1.5 では `on_sup` が最短待ち時間の直後に即座に真になるので、踏み替え周期が 1.15 秒 → 0.5 秒に短縮される。しかし両足支持相の横目標は依然として正中線のままなので、**体重移動は相変わらず起きず、ただ速く足を上げるだけ**になり、両足が同時に浮いている時間が増える。

だから正確な言い方はこうなる —— **「トリガの閾値がバグ」ではない。「両足支持相の目標(正中線)とトリガ(片側寄り)が、同じ量について矛盾していた」**。直すべきは目標側だ。これは「コードが悪い」話ではなく、**仕様が矛盾していた**話である。どちらの行も、単体で読めば正しく見える。「両足支持では重心を真ん中に置く」は静的安定として正しいし、「重心が支持足に乗ったら踏み出す」は歩行の教科書どおりだ。**2つを同じシステムに置いた瞬間だけ、両立しなくなる。**

提案されている修正は1行で、両足支持中の横目標を「真ん中 + $\alpha_{ds} \times$(支持足 − 真ん中)」にするだけである。$\alpha_{ds} \ge \alpha$ なら定常状態で初めてトリガが物理的な意味を持つ。**ただしこのフラグは実装されておらず、効果は完全に未検証である。** 合否バーだけは事前に固定してある —— **生存 ≥ 5 s / 両足浮き < 0.15 / 片足支持 ≥ 0.3**。実装して測る前にゴールポストを打っておくのが、この種の「1行で直る」提案を自己欺瞞から守る唯一の方法だと考えている。

### 3-7. この幕の持ち帰り

**① QP(全身制御)は、二足歩行だけの道具ではない。** 「制約を全部守りつつ二乗誤差を最小化する」という形は、動作検討に横断的に使える。把持なら、指の接触力を決定変数にし力閉包(force closure)を制約にすれば握力配分の最適化になる。腕の動作と握力を**同じ QP で同時に**解けば、「腕を動かした瞬間に握りが崩れる」類の問題は構造的に防げる見込みがある(未実装)。筋駆動なら、決定変数を筋活性 $a \in [0,1]$ に置き換えれば、生体力学で標準の**静的最適化(static optimization)**そのものになる(未検証)。

**② ただし、接触が減る瞬間に破綻する。** これが本章で最も転用価値の高い知見だ。接触点が減ると、接触力が張れる空間の次元が落ち、非駆動自由度の運動方程式を満たす解が消える。片足支持、片手把持、指を1本離す —— **接触が薄くなる局面では QP は実行不能になりやすい**。対策は2方向で、**接触を増やす**(質量ゼロで幾何だけ足す)か、**接触が薄い局面を設計に組み込む**か。後者を怠ると、自家撞着のように「接触スケジュールと制御目標が矛盾しているのに、誰も気づかない」状態になる。

**③ 「1行で直る」と分かったときこそ、先に合否バーを打つ。** 自家撞着は幾何1行で証明でき、修正も1行で書ける。だからこそ「直せば動くはず」と書きたくなる。だが素直に閾値だけ直した A/B は**悪化した**(3.34 → 2.17 s)。**直せることと、直せば良くなることは別**である。事前に固定した合否バーだけが、その区別を守ってくれる。

## 第4幕 — 借り物の体で、先に「本物の歩行」を見る

ここから時間を少し巻き戻す。**自前の体で QP を詰めていたのと並行して、私は「そもそも筋駆動の二足は歩けるのか」を別の体で確かめに行っていた。**日付が第3幕より前へ戻るのはそのためだ。

**第1幕で**、自作の進化探索が出した「前進 0.68 m の歩行」は、足の軌跡で測り直すと歩行ではなかった。**第2幕・第3幕で明示制御へ移っても、自前の体は 1〜3 秒で倒れたままだった。**そこで私は**自分の体と自分の探索を、いったん両方とも手放す**ことにした。手放した先が、他人が作って他人が検証したモデル、**LocoMuJoCo の HumanoidMuscle(92 筋)**である。

### 4-1. なぜ他人の体を借りたのか

本命は evis(MS-Human-700 由来の筋骨格ヒト、Apache-2.0 の自前資産)だ。それを置いた理由は二つ。

**事実①: 自前の 700 筋は GPU で学習が回らない。** 第0幕の「GPU の壁」に書いたとおりで、要点は、MJX(MuJoCo XLA)の計算グラフが約 28 GB に膨らみ、並列環境数を落としてもメモリ不足になり、通っても当時の CPU 実行と変わらない速度しか出ないことだ。

**事実②: 自前の体には「検証済みのお手本」が無い。** 借り物には、ある。25 軌道 × 10 秒、前進 **1.31 m/s**、股関節の左右逆位相 **−0.968** の熟練歩行(expert)が付いてくる。代わりに、借り物の既定の足は **22 cm × 6 cm の平板ブロック(箱足)**で、解剖学足も選べるが**その足用の expert は無い**。自前の evis(700 筋・自由度 85)にはお手本が無い代わりに、**骨格ごと作り替えられる**(実際、仙骨を 14°回して集団平均へ寄せた)。

> **借りた体には「検証済みのお手本」が付いてくる。自前の体にはそれが無い代わりに、骨格そのものを直す権利が付いてくる。**

私が取りに行ったのは性能ではなく**存在証明**だった。「この検証バーの下で筋駆動の二足が実際に歩ける」を一度自分の目で見ておけば、以後の失敗を「原理的に不可能」と「この体・この手法では未達」に切り分けられる。この切り分けができないまま自前で粘っていたのが、それまでの数週間だった。

**持ち帰り①**: 行き詰まったら「性能を上げる実験」より先に「**存在証明を取りに行く実験**」を置く。存在証明があれば、以後の失敗が「不可能」ではなく「未達」として扱える。


### 4-2. 行動クローン —— 観測 36 次元 → 筋活性 92 次元の、ただの回帰

使ったのは模倣学習で最も単純な**行動クローン(Behavioral Cloning, BC)**。入力は観測 36 次元、出力は 92 次元の筋指令、中身は隠れ層 1 枚・256 ユニット。「この状態のとき、お手本はこの指令を出していた」を教師あり回帰で丸暗記させるだけで、教師データは 25 軌道 × 10 秒・100 Hz の 25,000 フレーム。

なぜこれが手の込んだ進化探索に勝ったのか。**(1)** 進化探索の適応度は重心(Center of Mass, COM)の前進量ベースで、**前に倒れ込むと重心は前へ進む**。地形にはじめから偽物の峰が立っていた。BC には適応度地形が無い。**(2)** 進化戦略(Evolution Strategy, ES)は候補ごとのスカラーしか受け取らないが、BC は 25,000 フレーム分の 92 次元の正解ベクトルを受け取る。**(3)** お手本が既に検証を通っていた。

ただし BC が偉いのではない。効いたのは**検証済みの expert が存在する体を選んだ**一点だ。同じ BC を expert の無い解剖学足へ持っていくと、生存は **0.86 秒(剛体の足裏)/ 1.08 秒(柔らかい足裏)**しか保たない。実装では罠を三つ踏んだ。expert の行動は **62% が負の値**なので出力層は線形にしないと壊れる。評価時だけ行動を丸めると良い方策まで壊れる。足のボディ名 `foot_r/foot_l` は**存在しない**(正しくは `calcn_r/calcn_l`)ので、指標が黙って壊れる。

**持ち帰り②**: 「単純な手法が勝った」と書きたくなったら、**手法が勝ったのか前提条件が勝ったのか**を分ける。この場合は後者だった。

### 4-3. bc1 / bc2 / bc3 —— 壊れた checkpoint から本物へ

![箱のような足を履いた筋骨格ヒトが、左右交互に足を運んで歩き続けるクリップ](https://raw.githubusercontent.com/furuse-kazufumi/fullsense/main/docs/articles/assets/hillco_walk/clip_box_bc3.gif)

> **借り物の体(92 筋)＋箱のような足での模倣学習。**左右が交互に出て、どちらかの足が常に接地している。ここまでは本物の歩行だ。問題は、この安定が足の形に支えられていること —— それを次の幕で確かめる。

> 🔭 **[この体が動くところを、任意の視点で見る（箱の足）](https://furuse-kazufumi.github.io/fullsense/articles/assets/hillco_walk/walk_series_viewer.html?series=box)**
> 前進 +0.68 m のクリップを、真横・正面・真上どこからでも。足首から先が直方体であることが分かる。


合格条件は測る前に固定してある。以下これを**歩行判定バー**(`VERDICT_walks`、借り物モデル用)と呼ぶ —— 骨盤の前進 > 1.0 m、生存 > 5.0 秒、足の反位相 < −0.2(負 = 交互)、ゲート通過歩数 ≥ 4 の同時成立。第1幕で自前モデルに使った**足軌道の検証バー**(交互遊脚・クリアランス・支持足の滑り・骨盤高さ)とは別物で、こちらは借り物の体を判定する。評価は 1 エピソード 10 秒・8 エピソード平均、開始姿勢はお手本の途中からランダム(これが後で罠になる)。

| 方策 | 判定 | 前進(平均) | 反位相 | 生存 | 歩数 | 10 秒完走率 | 最良エピソード |
|---|---|---|---|---|---|---|---|
| bc1 | **不合格** | 0.333 m | −0.412 | 0.25 s | 0.5 | 0.00 | 0.546 m |
| bc2 | 合格 | 7.919 m | −0.514 | 6.13 s | 12.5 | 0.25 | 13.132 m |
| **bc3** | **合格** | **11.663 m** | **−0.448** | **8.84 s** | **17.4** | **0.38** | **13.348 m** |

**この表は n = 8 の 1 ドローである。** 同じ日にもう一度測ると bc3 は **11.052 m / 8.44 s / −0.427 / 完走 0.50** になった。読みどころは三つ。**bc1 は壊れた checkpoint だった**(出力が −45〜18 まで飛び、行動の絶対値が 1 を超えるフレームが 90%)。同じ手順で作った三つのうち一つが壊れ物だった。**bc3 の最良エピソード 13.348 m はお手本の 13.1 m / 10 秒 にほぼ並ぶ**。平均が落ちるのは 8 本のうち何本かが途中で転ぶからで、bc3 は「歩けないのではなく、たまに転ぶ」。そして**10 秒完走率は測るたびに 0.25 / 0.33 / 0.38 / 0.50 / 0.67 と振れる**。過去の記録には「62〜83%」とあるが、単一値として断定できる根拠は無い。


なお「10 秒間 骨盤を維持・前進 12.8 m・宙に浮く時間 0%」という、もっと強い記録も残っている。ただし**この数値の生ログは存在しない**。検証スクリプトの出力が標準出力だけで保存されていなかった。

**持ち帰り③**: 主張の強さと、それを支える**記録の残り方**は比例しない。標準出力しか出さないスクリプトは、**その時点では検証器でも、翌週には伝聞になる**。

### 4-4. 測定ミスの自己訂正 —— 「右足が擦っている」は、測り方の誤りだった

bc3 の歩容について「左右非対称で、右足がほぼ床を擦っている」という報告が上がってきた。**これは誤りだった。** 原因は検証スクリプト側で、足の持ち上げ量の基準に**すでに片足が上がっている中間フレーム**を使っていた。基準が高ければ持ち上げ量は小さく出る。しかも見ていたのは n = 1 である。8 エピソードで測り直すと**両足とも約 25〜29 cm 持ち上げ、ほぼ対称**だった(この再測定も記録は作業メモにしかない)。

痛いのは、**間違った結論から間違った次の実験が生えかけていた**ことだ。「対称性を学習させる報酬項を足すべきか」の検討が始まっていた。存在しない非対称を直すために報酬を 1 項増やし、それが別の何かを壊し、それをまた別の報酬で直す —— 何度も踏んだ道である。

**持ち帰り④**: **n = 1 の測定から設計変更を決めない。** とくに「非対称」「劣化」「改善」のような**差**を主張するときは、基準の取り方そのものを疑う。差は基準の誤りをそのまま増幅する。

## 第5幕 — その安定は「松葉杖」だった

### 5-1. 足を縮めるだけで、歩行は消える

借り物の既定は箱足で、**足首から先が幅 6 cm・長さ 22 cm の平らな直方体**に置き換わる。解剖学的な足のメッシュは残っているが表示専用で、物理的には接地していない(実測した半寸法は (0.112, 0.03) m = 全長 22.4 cm × 全幅 6.0 cm)。

疑問はこうだ。**bc3 の安定は、方策が獲得した技能なのか、足の形なのか。** 言葉では決着しない。決着させる方法は一つ、**足を縮めることだ**。方策も報酬も学習も触らず、足裏の接地面だけを縮めて同じ評価をかける。これが切除実験(ablation、要素を削って寄与を測る実験)になる。

| 足裏スケール | bc3(BC)前進 / 生存 / 10 秒完走 | amp_box3(RL)前進 / 生存 / 10 秒完走 |
|---|---|---|
| ×1.0(22.4 cm) | **10.30 m / 7.89 s / 0.33** | **10.65 m / 8.33 s / 0.67** |
| ×0.6(13.4 cm) | 1.81 m / 1.58 s / **0.00** | 1.91 m / 1.76 s / **0.00** |
| ×0.4(9.0 cm) | 1.17 m / 1.20 s / 0.00 | 1.23 m / 1.40 s / 0.00 |
| ×0.25(5.6 cm) | 0.92 m / 0.92 s / 0.00 | 1.12 m / 1.09 s / 0.00 |

**足裏を 6 割にするだけで、前進は 10 m 台から 1.8 m 台へ落ち、10 秒完走率は BC 0.33 / RL 0.67 からどちらも 0.00 へ落ちる。** なおこの表の過去版とは**完走率だけが食い違う**(元の記録は ×1.0 で BC 83% / RL 50%)。生ログが無く照合できない。**前進距離と崩壊の形は完全に再現するが、完走率は n = 6 では単一値として扱えない。**


最も重要なのは、**RL の列が BC の列と同じ形で崩れている**ことだ。`amp_box3` は bc3 を起点に敵対的模倣(Adversarial Motion Priors, AMP)で 1200 万ステップ追加学習した方策だが、足を 6 割にした瞬間 BC と区別がつかなくなる。**この歩行の安定を担っていたのは学習の巧みさではなく平板な足の形だった。**

ここから「本物のロバスト歩行」の定義が決まる。**松葉杖を外して歩けること、すなわち解剖学的な足で歩けること。** ただし解剖学足に替えると体は「足だけ違う同じ体」にはならない。距骨下(subtalar、足を内外にひねる関節)と中足趾節(metatarsophalangeal, MTP、足指の付け根)が復活して自由度が 19 → 23 に増え、増えた関節は観測ベクトルの**末尾ではなく途中に挿入される**ので、箱足用の方策を列コピーで移す手は不正になる。そして**解剖学足用の expert は存在しない**。

**持ち帰り⑤(この幕の中心)**: **成功の原因が技能なのか形状なのかは、その形状を縮めれば分かる。** 設計は 3 点。(1) **一変数だけを連続的に動かし**、「どこで崩れるか」でなく「**崖があるか**」を見る。(2) **学習した方策と学習していない方策の両方に同じ切除をかける**(片方だけだと「その方策が下手だっただけ」と混同する)。(3) **連続量と二値の両方を見る**(前進距離は 10.3 → 1.8 と落ちるだけだが、完走率は 0.33 → 0.00 と**底を打つ**)。あなたの実験でも、成功が自分の工夫か環境の親切さかを分けたいなら、**親切さの方をパラメータにして削る**のが最短の答え合わせになる。

![顎に指を当てて「何か主語がデカくない…?」と訝しげに考える明美](https://raw.githubusercontent.com/furuse-kazufumi/fullsense/main/docs/articles/assets/bazue_all/093.jpg)
> 🗒️ *「何か主語がデカくない…?」— 「歩けた」の主語は誰か。借り物の体で、箱のような足で、というただし書きが全部抜けていた*（© Forbidden shibukawa / SHUEISHA・『スナックバス江』）

### 5-2. RL fine-tune の 3 連敗と、ピークが出た時刻

BC はお手本の分布の上でしか歩けない。ならば閉ループの強化学習(Reinforcement Learning, RL)で回復を学ばせればよい。素直にそれをやって、負けた。

負ける前に効いた修正が一つある。割引率(discount factor, γ)を **0.99 → 0.997** にしたことだ。dt = 0.01 秒で γ = 0.99 なら見える未来は **約 1 秒**しかない。この体は転ぶまでに 2 秒前後かかる。つまり γ = 0.99 の方策にとって**2 秒後の転倒は存在しない未来**であり、学習は「1 秒だけ速く動いて転ぶ」を正しく最適化していた。**持ち帰り⑥**: 割引率を「なんとなく 0.99」で置かない。**dt を掛けて秒に直し、失敗事象がその窓に入っているかを確認する。**

そのうえで 3 系統・約 10 設定が負けた。**タスク報酬 PPO** は学習率を落としても劣化が遅れるだけで 7.85 → **2.5 s**、リターン正規化版は 8.8 → **1.9 s**。**DeepMimic 追従**は 5.8 → **3.7 s** の漸減、アンカーを消すと **0.9 s** へ崩壊(訓練終了時 生存 0.98 s / 完走 0.00)。**AMP** だけが勾配ペナルティ(gradient penalty, GP)付きで**初の単調回復**(0.85 → 2.2 s)を見せたが**約 2.0 秒で頭打ち**(訓練終了時 2.47 s / 完走 0.00)。解剖学足で試した版は**195 本の評価すべてで歩行 false** だった。

本当に効く証拠は、ピークがいつ出たかにある。箱足の RL ログを全部走査すると、`rl_box_v1` のピーク 8.76 s は **53,760 ステップ(warm-start 直後)**、`rl_box_v2` の 7.89 s は **43,008**、`amp_box3` / `rl_box_track2` / `rl_deepmimic` の 8.81 s はいずれも **107,520** で出ていた。しかも 生存 8.81 s / 前進 11.539 m / 反位相 −0.487 / 15.7 歩 / 完走 0.67 という**まったく同じ 1 行**が 6 本のログ(`amp_box`・`amp_box2`・`amp_box3`・`rl_box_track`・`rl_box_track2`・`rl_deepmimic`)に現れる。同じ乱数種で同じ BC 方策を評価しているので当然そうなる。**つまりこれは RL の成果ではない。学習を 1 回も適用していない BC 方策そのものの点数である。** 各ログの最終行はすべて生存 0.98〜2.47 秒・完走 0.00 で、約 2000 万ステップの追加学習が**始点より良い点を一度も出さずに終わった**。

**持ち帰り⑦**: 学習曲線は、最良値そのものより**最良値が出たステップ番号**を見る。それが warm-start 直後なら、その最良値は学習ではなく初期化の成果だ。

### 5-3. なぜ訓練中は良く見えたのか —— 参照状態初期化の罠

**訓練中の報酬は上がっていた。** 犯人は**参照状態初期化(Reference State Initialization, RSI)**である。開始姿勢をお手本の途中からランダムに選ぶ標準的な良い手法だが、**転倒するたびに次のエピソードはお手本の良い姿勢から再開される**。1.5 秒で崩れる方策でも 1.5 秒ごとに引き戻されるので、平均報酬は「1.5 秒ぶんの良い挙動」を積み上げ、訓練の集計は右肩上がりになる。評価では引き戻しが無い。1.5 秒で崩れる方策は、1.5 秒で崩れる。

同じ罠は GPU 側でも再現した。借り物の 92 筋を **6000 万ステップ・81 分** 完走させたとき、報酬は 51 → **197.65** へ単調に上がった(この実行は、付録 B に載せた「1024 環境で約 1000〜1150 steps/s」とは別構成である。並列環境数が違ったと考えているが、当時の起動設定は記録に残っておらず**未確認**)。だが描画して私が目で見ると、**0.9 秒・前進 0.37 m のよろめきで転倒**していた。報酬 197 の正体は「1 秒ぶんの前進バースト × 約 100 ステップ」だった。

**持ち帰り⑧**: 訓練指標と評価指標で**エピソードの始め方が違う**なら、その二つは別物として扱う。**主張は必ず決定論・連続再生の側で書く。** なお BC の歩容は**細い尾根の上にある解**で、初期の数十更新で尾根から落ち(7.4 → 0.9 秒)、AMP + GP で約 2 秒までは登り直せるが元に戻らない。落ちた先の盆地が別物なのだと考えている(推測)。実測として言えるのは、**どの系統も BC の始点を超えた記録が 1 本も無い**ことまでだ。

## 第6幕 — 足そのものを設計する(受動機構)

### 6-1. 制御を殴るのをやめて、体の仕様を書いた

ここまでの幕はぜんぶ「制御をどう賢くするか」だった。**方策の側だけを殴っていた。** 方針が変わったのは、私が出した次の 3 行の見立てからだった。

> - 足首から先は、**遊脚(swing、浮いているとき)は脱力してニュートラルへ戻る**。
> - **接地したら地面に倣うだけ**。
> - **後方への蹴り出しだけが能動**。

これは制御の要求仕様ではない。**体の仕様**である。人間の足首から先が四六時中フルに能動制御されているという前提そのものを疑っている。無負荷の足は受動組織の張りで中立姿勢に戻り、荷重がかかればその姿勢は地面のかたちに上書きされる。だから制御器がわざわざ「足を平らに保て」と毎ステップ命令しなくていい。それまでこの体では、足首・距骨下・中足趾節の 3 関節を**受動剛性ゼロの、制御器が全部支えるべき関節**として扱っていた。

この見立てを、報酬項ではなく**物理モデル側に埋める受動機構**として実装した。「仕組みは極力**数学で説明できる形**にする」という規律があるからで、**説明できない仕組みは、後で嘘をついても気づけない**。受動バネの復元トルクは関節角の 1 次式なので予測に学習が要らず、バネ定数を 0 にすれば効果が消えるという A/B が取れる。そしてなにより、**強化学習に壊されにくい**。方策に入れた工夫は方策と一緒に壊れるが、体に入れた工夫は残る —— **と考えている**(この記事の範囲では、機構の有無で 0.09 秒しか差が出ておらず、直接の裏付けは取れていない)。

### 6-2. 実装 —— 部品は三つだけ

**(a) 遠位関節の受動バネ + 減衰。** 足首・距骨下・趾の左右 6 関節にニュートラル姿勢へ戻るバネと減衰を立てる。

```math
\tau_{\text{passive},j} = -k_j (q_j - q_{j,0}) - b_j \dot q_j, \qquad k = 8.0,\ b = 1.0
```

肝は、**バネの自然長をモデルのニュートラル姿勢そのものに置いている**ことだ。「どこへ戻すか」を人間が数字で決めていない。自由に決めているのは剛性と減衰の二つだけになる。

**(b) 柔らかい足裏。** 足と床の接触を柔らかくする(時定数 0.04・減衰比 1.5、転がり摩擦 0.001)。**剛体どうしの接触だと、足裏が地面に「倣う」余地が幾何学的に存在しない。**

**(c) 位相で式が切り替わる報酬。** 接地中(踵と前足の低い方が 0.10 m 未満)は `exp(−150(z踵 − z前足)²)` で「高さを揃えろ」、遊脚中は `exp(−4(Δ足首² + Δ距骨下²))` で「ニュートラルへ戻せ」。係数が桁違いなのは**測っている量の単位が違う**ため(高さの差とラジアン)。単位が違うのに係数が同じなら、片方が事実上効いていない。**報酬項を足すときは、その項が動く数値レンジを先に見ておく。**

### 6-3. 報酬を書く前に、その関節が本当に動くかを確かめた

苦い前科は第0幕に書いた。腕に駆動筋が 1 本もないモデルで 11 回の実験を回し、その全部が歩行不成立になった件だ。数十時間の GPU 時間が、静的チェック 1 回で避けられたはずの失敗に消えている。だから今回は順番を守った。

今回は順番を守り、報酬を書く前にモーメントアーム行列を読んで**モーメントアームがゼロでない筋を数えた**(足首 12 筋、距骨下 12 筋、趾 4 筋)。但し書きが二つ。これは**借り物(92 筋)の解剖学足**の数字で、本命 evis(足は各 1 モータ・受動剛性ゼロ)の数字ではない。そして**この検証の実行ログは残っていない**。出典は作業メモだけである。

機構が設計どおり働いたかについても、記録は弱い。接地中の踵と前足の高低差が平均 3.1 cm(約 20 cm の足に対して約 9°)、遊脚中の足首がニュートラルから平均 9.4° 以内、という記録はある。私の見立ては**作業メモに残る記録の上ではその通りの姿勢分布として現れていた**。ただし**この 2 つの数値も生ログと計算スクリプトが見つからず、再測定するまでは「検証済み」とは書けない**。

### 6-5. 自分の歩容をお手本にする試みは伸びず、この解は本命の体にも移らなかった

「この足で持続できた歩容」を新しいお手本にすれば近づけるのではないか、と `footflat1` のベスト方策を 60 回ロールアウトして参照を作り直した(実ファイルは (6906, 46)、100 Hz で 69.06 秒相当)。なお「60 本中 46 本を採用した」という記述が残っているが、**46 は配列の列数(関節位置 23 + 速度 23)であって本数ではない**。採用本数を示すログは見つからず、数字が偶然一致しただけの可能性が高い —— 未確認として書いておく。結果は plateau で、ピーク生存は 2.07 → 1.34 → 1.23 秒と**元を超えない**。

そしてこの受動機構は**借り物の体の上での成果**である。本命 evis に同じ受動バネを移植する A/B を取ると、**立位の生存が 9.34 秒 → 5.08 秒に悪化した**(evis 側の足機構テストによる。第 3 幕の全身 QP の 1.46 秒とは保持条件が違い、直接比較はできない)。evis の足はすでに**平らな剛体パッド**を履き接触も固めてあり、「倣う」より「踏ん張る」設計だからだ。借り物の解剖学足は逆に受動剛性が低く、**受動バネはそのふにゃふにゃさを埋める部品として効いていた。**

> **持ち帰り⑨**: 「良い機構」は普遍解ではなく、**その体の欠けている性質を埋めたときだけ効く**。移植前に、移植先で同じ性質が欠けているかを確かめる。ここでは A/B を 1 回取るだけで判別できた。

## 第7幕 — ズルの経路を、報酬の側から塞ぐ

### 7-1. 「お辞儀みたいな動きだね」

![本命 evis が前傾しながら床の上を移動していくクリップ](https://raw.githubusercontent.com/furuse-kazufumi/fullsense/main/docs/articles/assets/hillco_walk/clip_evis_attempt.gif)

> **前進 2 m と報告されたラン。**骨盤のロールは 0 → 204°、頭は 1.46 m から 0.22 m まで落ちている。歩いているのではなく、床を転がりながら前へ出ていた。動きを見れば 2 秒で分かることに、数値だけを見ていた私は気づかなかった。


本命の evis に戻る。全身制御の探索を回していたとき、私は動画を見てこう言った。

> **「お辞儀みたいな動きだね」**
> **「頭で距離を稼いでいるだけの学習になっていないか」**

数値の上では、そのランは前進 2 m を稼いでいた。実データを当てたら、骨盤のロールが 0 → **204°**、ピッチ **91°**、骨盤の高さ 0.94 → **0.16 m**、頭の高さ 1.46 → **0.22 m**。**床を転がりながら 2 m 進んでいた。**

### 7-2. 同じ穴が、報酬の側にも開いていた

重心の前進が嘘をつく理屈は第1幕の倒立振子で書いた(足を固定したまま 30° 倒れるだけで、重心は約 0.49 m 進む)。ここで書くのは、**同じ穴が報酬側にも開いていた**という話だ。

前進報酬は重心の速度を買っていたから、その約 0.49 m は歩行と同じ点数で買われる。**報酬関数は「歩け」と言っているつもりで、「重心を前に出せ」としか言っていない。** 対策は第1幕で書いた足基準の前進(両足中点の変位)と同じものだが、ここで大事なのは、**同じ量を報酬と検証器の両方に見せている**ことだ。自作の進化歩行を偽物と摘発した検証器も、前進を両足中点で測る。docstring がそのまま方針になっている。

> *Never trust the metric — check the pose. Distance is measured at the FEET (support centre); a topple advances the COM but not the feet.*
> (指標を信じるな、姿勢を見ろ。距離は足で測る。転倒は重心を進めるが、足は進めない。)

測り方は一度で正解に着いたわけではない。骨盤の前進速度 → 全身重心 → 両足中点、と 3 段階の変遷が残っている。そして第 2 段には**実装バグが入っていた**。部分木の線速度を返す関数がこの経路では埋められず、毎ステップ 0.0 を返していた。前進報酬は**定数**になり、動くことへの勾配がゼロだった。学習は正常に見え、報酬も上がっていた。だが上がっていたのは前進以外の項だけで、前進報酬は目的関数として死んでいた。見つけたきっかけは、私が指標の値そのものを不審に思ったことだった。

> **持ち帰り⑩**: **速度系の派生量は「計算されているか」を実測する。** 0 は「値がない」ではなく「値が 0」として下流に流れる。1 行のアサーションで防げる事故だが、防がなければ数百万ステップが無意味になる。

### 7-3. 疎な即死と密な勾配は、必ず対で置く

倒れる過程で稼ぐ経路を塞ぐため、**頭が床に近づいたらエピソード終了**を足した。閾値 0.9 m は実測から取ったマージンで、頭の高さは立位 約 1.47 m、歩行中 約 1.43 m。歩行中から **0.53 m 下**なので、自然な上下動では絶対に切らず、ダイブ・膝つき・前転だけが切る。ただし**即死ラインだけを置くと「最後のフレームでラインを避ける」方策が最適になる**。そこで頭の高さ 1.0 m 以上では厳密に 0、下回ると二次で効く片側ペナルティを対で置いた。

> **持ち帰り⑪**: **疎な終了条件と密な勾配は、必ず対で置く。** 終了条件だけなら境界ぎりぎりで踊る方策が最適になる。ペナルティだけなら罰を経費として払って越える方策が現れる。両方なら「常に離れていろ、越えたら終わり」になる。**閾値で何かを禁止する設計すべてに効く**と考えている。

傾き判定を書くときに**軸の同定をやり直した記録**も残っている。各ルートヒンジを摂動して読み直すと、名前が `pelvis_tilt` の自由度は世界のピッチ、`pelvis_list` はロールだった。旧コードは 1 番目を進行方向として読んでいたので、「捻れ防止」のつもりのペナルティは**前傾を罰していただけ**で、本来対象だった 112°の体幹の捻れには何もしていなかった。横方向だと思って読んでいた速度成分が実は上下方向で、「横ドリフト罰」が**歩行の上下動を罰していた**という記録もある。どちらも**変数名の意味と、その配列要素の実際の意味が違っていた**。

終了条件には、いちばん寒い一行も入っている。**きれいな 10 秒立位として報告されたランが、実は 9.3 MN(体重の 160 万%)の接触力を出していた**のだ。対策は「関節速度の最大値が 100 rad/s 未満」という常識条件を足すこと。**姿勢だけを見ていると、物理が壊れていることに気づけない。**

### 7-4. では、歩いたか —— honest_walk 1〜5 の実測

ここまでの設計を全部入れて回した学習が `honest_walk1` 〜 `honest_walk5` である。**結論から書くと、5 本のうち歩行に到達したものは無い。** walk1・walk2 は**評価行が 1 本も無い**まま終了、walk5 はステップ 0 の評価のみ。**目標ステップに到達したランはゼロ**で、有意な曲線が残るのは walk3(1966 万で打ち切り)と walk4(1310 万で打ち切り)だけだ。

walk3 は「転ばないこと」だけを学習した。報酬 65.63 → **442.32**、エピソード長 0.42 → **1.25 秒**、生存率 0.99。数値だけ見れば順調である。そこで最終チェックポイントの姿勢を 1 コマずつ検証器に通した。

|---|---|---|
| 立位維持 | **1.69 s** / 5.99 s | — |
| **足基準の前進距離** | **−0.22 m**(後退) | > 0.5 m で合格 |
| 骨盤高さ 最小 / 頭の高さ 最小 | 0.164 m / **0.137 m** | 立位 約 0.94 / 約 1.47。それぞれ 0.6・0.9 を割れば転倒 |

報酬 442 という数値の裏で、**実際の体は約 1.7 秒で頭から崩れ、足は 22 cm 後退していた。** 自作の進化歩行を摘発したときと**同じ構図が、honest 淘汰の報酬を入れた学習でも起きている。** walk4 は逆で、エピソード長 **9.44 秒**・生存率 1.00 と立つほうは大幅に良いが、足基準の前進速度が **0.123**。このプロジェクト自身の局所解検知器は「生存 > 3.0 秒 かつ 前進速度の絶対値 < 0.15」を「動かない窪み」と定義しており、walk4 はぴったり当てはまる。**倒れないことだけが上手くなり、動くことをやめた方策**である。

正直な注記を二つ。**honest_walk1〜5 の起動フラグはどこにも記録されていない。** ログのヘッダは 1 行だけで、どの施策が有効だったかを**確認できない**。したがって「これらの施策が実際に効いたか」は、この 5 本からは判定できない。もう一つ、ログの自己めり込み量は**指標そのものが壊れている**(全 91 の自己衝突ペアから求めた物理的最大が 134 mm なのに 248 mm・482 mm が記録されている)ので引用しない。


### 7-5. 塞いでも穴は残る

honest 淘汰の設計を、多数の並列エージェントで敵対的に監査させた。**塞いだつもりの経路に、まだ二つ穴があった。** 足基準の前進には「足を上げる」要件が無いので両足を床につけたまま滑らせる走法で満点が取れ、片足を宙に振っても両足の中点は前へ進む。

さらに介助バーの実験から、もっと本質的な教訓が出ている。「バー荷重が 100% を超えているのは、宙に浮いているのでは?」という私の一言で発覚したのは、報酬が**水平方向のグリップ力しか罰していなかった**ことだった。実測すると水平 20.8% / **鉛直 100%BW** / 足の接地荷重ほぼ 0% / 踵の高さ 0.60〜0.69 m。**完全にぶら下がっていた。** 「荷重 135% → 90% への改善」に見えていたものは**上手くぶら下がる学習**だった。3 次元の総バー力に直すと、次は接地率 2% / ぶら下がり率 90%。最終的に効いたのは報酬ではなく**物理側の容量制限**で、バーの鉛直上限が 2400 N = 体重 590 N の 4 倍あった。

> **持ち帰り⑫(この幕の中心)**: **報酬で禁止するより、物理的に不可能にするほうが強い。** 順序は「①ズルの経路を列挙 → ②物理的に封じられるものは封じる → ③封じられないものだけ、疎な終了条件 + 密な勾配で罰する → ④監査で穴を再列挙(必ず残る)」。**穴が残ることを前提に、監査を工程に組み込む。**

まず作ったのが 310 行のデスクトップアプリ。肝は**機体の自動判別**で、保存されたロールアウトの**列数(= 一般化座標 nq)だけを見て、どの体のデータかを当てる**(37 = 借り物の箱足、36 = evis の 100 筋版、97 = evis の torque-twin、23 = 借り物の解剖学足)。**別々の日に別々の体で走らせた結果を、同じ窓に順番に放り込んで見比べられる。** 途中で踏んだ罠も残っている。torque モデルの XML はメッシュの場所を Linux 側の絶対パス形式で焼き込んでおり、Windows 側から読むとモデルが真っ白になる。借り物の XML はメッシュ名が内容ハッシュで参照先の指定も無く、単体ではロードできない。**気づかないと「モデルが壊れている」と誤診する** —— 可視化ツールのバグと研究対象のバグの区別がつかなくなる。

## 第9幕 — これから: 歩行を「言葉」として設計し直す

### 9-1. なぜ「物理を速くする」ではなく「構造を変える」なのか

自前の体に対する end-to-end の強化学習は、`honest_walk3` が 1966 万ステップで報酬 442.32・エピソード長 1.25 s に到達しながら実姿勢では 1.69 秒で転倒、`honest_walk4` が 9.44 秒立つが 0.123 m/s、という状態で止まっている。ここで自己訂正を 1 件。「前進速度が 1.253 → 0.42 へ**悪化**した」という読みは誤りだった。1.253 はステップ 0 の未学習方策が弾道的に前へ倒れている数字(エピソード長 0.42 秒)で歩容ではない。正しい所見は「**1966 万ステップ使っても 2 秒しか立てない**」である。

計算が足りないなら速くすればいい、と最初は考えた。実測がそれを否定した。ソルバ反復 100 → 4 で**約 1.6 倍のみ**、100 → 8 は**空振り**、接触上限 1000 → 200 も無効(実際のピーク接触数は 114)。そして内訳を測ると、**壁時計時間の 67% は方策勾配の計算、物理は 22%** だった。物理を**無限に**速くしても全体は**最大 1.28 倍**で頭打ちになる。これが**アムダールの法則(Amdahl's law)**のもっとも身も蓋もない現れ方だった。(この内訳の一次ログは今回の調査では確認できていない。)

計算量の削減は三つの軸に分けて仕分けた。**軸 1(決定変数 × 頻度)**は 49 次元 × 100 Hz に対し接地点なら 1 歩あたり 2 スカラーで約 490 分の 1、**桁で減る**。**軸 2(収束サンプル数)**は**未実測**で、測るまで主張しない。**軸 3(1 サンプル単価)**は上記のとおり**ほぼ効かない**。**桁の削減は、ノブからではなく「問題そのものを小さくする構造変更」からしか来ない。** ただし軸 2 が未実測である以上、これはまだ**決定変数の軸でのみ裏付けがある**主張にすぎない。

### 9-2. 構造変更の中身

> **以下はすべて設計であり、2026-08-11 時点で実装は 1 行も無い。数値は実測ではなく設計上の見積もりである。**

新しい設計は、動きを**言語**として扱う予定だ(hillco = 肉体言語モデル)。運動シナジー(muscle synergy、多数の筋をまとめて動かす少数の協調パターン)を**語彙**、その時間的な並びを**文**と見なす。上層は離散ポーズトークンの状態機械で、どの基準を狙うか(接地点・重心目標・上半身タスク)を選ぶ。下層は第3幕と同じ全身 QP による連続追従。面白いのは**「腰」という中間層が要らなくなる**ことだ。足裏が地面に倣うのも、腰が重心目標に倣うのも、**すべて「基準に倣う連続サーボ」という同じ 1 つの仕事**になる。

1 つのポーズには、連続埋め込み(学習・照合用)と **128 ビットの内容ハッシュ**(辞書キー用)、硬さ、移行速度を持たせる。分けるのは、ハッシュには**雪崩効果(avalanche effect)**があり 1 ビット違うだけで出力が全く別になるからだ —— **ハッシュは汎化に使えない**。128 ビットは誕生日問題の勘定による(64 ビットだと約 40 億個で衝突が現実的になる)。探索は、遷移の初期重みを「想定遷移時間の逆数」に置き、重み順に探してバランスが取れる候補を 3〜5 個見つけたら打ち切る。**学習するのは遷移の重みだけで、語彙は固定・人が読める**。生存の不変量は**捕捉点(capture point)**、すなわち「重心 + 重心速度 / √(g / 重心高さ)」に置き、監視する芯はその**余裕**にする(**左右が先に尽きる**)。拡張の契約は「追記のみ・次元固定・分布外は fail-closed」。既存の**ベクトル量子化(Vector Quantization, VQ)**ベースの手法との違いはここで、**VQ は語彙を追加すると全トークンが動いてしまう**。

支えている観察を一つ。**肉体言語の係数の数は、末端が届く範囲(到達多様体)の内在次元で決まり、関節の数では決まらない。** 脊椎 3、四肢 4、指 2、**手全体で 2〜3**(20 以上の自由度が把持では 2〜3 のシナジーに潰れる、Santello ほか 1998)、全身合計 **約 31 係数**。ただし**この数は設計上の見積もりであって、実装・実測による検証は未了である。**

### 9-3. 超えなければならない零点と、まだ言えないこと

「主張する前に零点(null、何もしないときの成績)を測り、上回れ」という規律がある。零点は体ごとに違うので主語を付ける。第1幕で並べた 3 つの零点のうち、**新しい設計が超えるべきは 100 筋変種の 0.50〜0.53 秒**である。

> **`footflat_long2_best`: 借り物の解剖学足・歩行判定 true・生存 5.30 s・前進 6.587 m・11.3 歩・足の交互 −0.534**(45 本中 1 本。**10 秒完走率は全評価で 0.00**、訓練終了時は 3.77 s / 4.287 m へ落ちる)

正直に言えないことも並べておく。**PoC は未着手**で、128 ビットハッシュも内容アドレス状態機械も未実装である。**アイデア自体は新しくない**(Motion Matching / MotionGPT / VQ ベースの先行がある)。新しいと言えるのは「筋駆動の物理シミュレーション上で、人が読める語彙・追記のみの契約・ハッシュ鍵を同時に満たす実装が見当たらない」という一点だけだ。**横バランスの壁は場所しか分かっていない**(足幅 30 cm でも 3.2 秒、足裏パッドの横方向の復元モーメント上限は約 25 N·m、**横を直す権限は股・脊柱・腕の角運動量にあり足首には無い**)。そして**その壁の一部は物理ではなく私たちのコードの欠陥だった**。歩行 QP の踏み替えトリガは、**定常状態では原理的に発火しない**(幾何と A/B の実測は第3幕)。しかも**発火可能にするだけでは悪化した**。直すべきは目標側で、その修正はまだ実装されていない。

## 教訓

**1. 数値スコアは「意図」ではなく「測った量」を最適化する。** 実例: 骨盤ロール 0 → 204°で床を転がりながら「前進 2 m」を稼いだラン。対策は前進を**足**で測ること。ただし監査でこの対策にも穴が見つかっている(滑らせる走法、片足を振るだけ)。

**2. 派生量を信じず、物理エンジンの一次量で判定する。** 実例: 部分木の線速度を返す関数が、ある経路では**計算されず常に 0.0 を返し**、前進報酬の勾配が最初からゼロだった。

**3. 零点を先に測り、上回ってから主張する。零点には主語を付ける。** 実例: 100 筋変種の無制御転倒 0.50〜0.53 秒に対し、同じ 100 筋での直立は**その 26 倍**まで伸びたので技能と呼べる(内訳は第0幕)。零点は体ごとに違うので、**どの体の零点かを書かないと比較が壊れる**。

**4. 松葉杖を疑い、縮めて確かめる。** 実例: 箱足を 0.6 倍に縮めると模倣は 10.30 → **1.81 m**・完走率 0.33 → **0.00**、強化学習は 10.65 → **1.91 m**・0.67 → **0.00**。介助バーも、軽い介助なら 10 秒完走だが**介助 0 にすると 3.1 秒で転ぶ**。

**5. 報酬で罰しても、物理的に可能な抜け道は残る。** 実例: 介助バーの報酬は水平方向の力しか罰しておらず、方策は鉛直方向にぶら下がった。最後に効いたのは報酬ではなく、バーの容量そのものを絞る物理側の制限だった(数値は第7幕)。

**6. 報酬を書く前に、その関節が本当に駆動できるかを測る。** 実例: 借り物の 92 筋モデルは**腕に駆動筋が無く**、腕が受動的に 60°暴れる死重になっていた。**この 1 つの静的チェックで、11 回ぶんの GPU 実験が回避できた。**

**7. 早計に打ち切らない。長いランは完走させる。** 実例: AI は解剖学足の学習を「約 2 秒で頭打ち」と判断して止めていた。私が「腰を据えて回せ」と言って中断なしの長いランを 2 本完走させたところ、**この足で初めて歩行判定バーを通った**(記録は第6幕)。

**8. ノブでは桁は減らない(アムダールの法則)。** 実例: ソルバ反復 100 → 4 で 1.6 倍、100 → 8 は空振り。壁時計の 67% が勾配計算なので物理を無限に速くしても 1.28 倍が天井(**この内訳の一次ログは未確認。ソルバ反復の A/B は実測**)。この結論自体、「ソルバを詰めれば数倍から数十倍は行くはず」という **AI の見積もり**を、実測が訂正したものである。

**9. 数値の監視と、実姿勢の監視は別物。二段で持つ。** 実例: `walk4`(生存 9.44 秒だが 0.123 m/s)は数値側**だけが**捕まえ、`walk3`(報酬 442)は姿勢側**だけが**捕まえた。

**10. 撤回は、結論だけでなく経緯ごと残す。** 実例が二つ。「受動剛性ゼロのふにゃふにゃの操り人形が転倒の真因」という診断は一次資料の側で既に撤回されている(接地させて測り直すと、700 筋モデルは平均活性 2.8% で静的平衡を張っていた)。もう一つは、この原稿自身が一度書いた「ビューアの生成スクリプトが存在しない」で、検索の仕方が悪かっただけだった。**撤回した記述を消すと、次に同じ間違いを踏んだとき気づけない。**
