# 骨と筋だけの人体を、自宅の CPU で立たせ・掴ませ・飲ませ・踊らせた全記録 — 700本の筋肉とマスコット「evis」、正直な負けと勝ち

> 対象: ロボット・バイオメカニクス・進化計算・MuJoCo・モーションキャプチャに興味がある人 / 「筋肉で動く人体モデル」や「解剖学的な人体を自宅で動かす」ことに興味がある人 / 良い結果より**正直な内訳と、詰まって直すまでの過程**を読みたい人。
> 前提知識: Python が読めれば十分。制御・生体力学・mocap の用語は都度かみくだきます。
> 数値はすべてノート PC の CPU で実測。この記事は成功談ではなく、**「一方は正直に負け、一方は勝った」その両方を同じ物差しで測り、詰まったら推測でなく測って直した**、ひと繋がりの記録です。

この記事は、これまで別々に書いた3本の連作 —— 「立つ・掴む・運ぶ」「飲む(バグ追跡)」「evis マスコット化(mocap)」—— を、時系列と因果でひと続きにまとめた**決定版**です。長いので、興味のある章から読んでも構いません。

## 0. 3行まとめ(先に結論)

- **骨・腱・700本の筋肉でできた全身の人体モデル**(中国 LNS Group の `MS-Human-700`、ICRA 2024、Apache-2.0)を、自宅の CPU 上の MuJoCo に載せ、**筋肉を1本ずつ進化で動かして**「立つ」「掴む」「運ぶ」「飲む」をやらせ、最後は**マスコット「evis」**に仕立てて **mocap で踊らせ・箸で食べさせた**。トルクのモーターではなく、**縮む力しか出せない筋肉**で動かすのが肝。
- **立位は正直に負け、把持は勝ち、運搬は部分的な勝ち(3分の1)**。何もしなければ約1秒で崩れる骨格を、閉ループ制御で崩落を典型2.5秒まで遅らせたが、6秒は立てなかった(負け)。一方、肩を固定した腕モデルの**81本の筋肉の手は、机の水ボトルを掴んで0.82m持ち上げ保持**(勝ち)。「命令した場所へ運ぶ」を足すと部分成功(半分)。**なぜ課題によって勝ち負けが分かれるのか**が前半の主役だ。
- **後半は「測って直す」二連発**。「飲めた」と思った動作は、人間の一言「口に入っていない」で棄却され、追うと**ボトルが床をすり抜けて地中に沈むバグ**(keyframe の番号ずれ)に行き着いた。**0 を一つ正しい場所に挿す**だけで直った。そして骨格を evis と名付け mocap を移植すると、今度は**「腰が老人みたいに曲がる」**猫背バグ。推測をやめ関節角を測ると、真犯人は「マーカーの高さの取り違え」だった。**推測する前に測れ**——それが通奏低音だ。

> honest な但し書きを先に: 立つ・掴む・運ぶ・飲む(腕)は**筋肉で駆動する本物**だが、evis の踊り・箸・飲む所作の一部は**キネマティック再生(関節角を直接与える演出)**が混ざる。**どこが本物でどこが演出か**は各所と最終章で明記する。

## 1. 用語(先に地図)

長い記事なので、言葉だけ先に地図にしておく。知っている行は飛ばして構わない。

| 用語 | かみくだき |
|---|---|
| 筋骨格モデル(musculoskeletal model) | 骨・関節だけでなく**筋肉と腱**まで持つ人体シミュレーション。今回は700本の筋肉つき全身 |
| 筋アクチュエータ(muscle actuator) | 「筋肉」を動力源にした駆動。モーターと違い**縮む(引く)力しか出せず**、0〜1の活性で力が決まる非線形な代物 |
| 自由度(DoF / degrees of freedom) | 独立に動ける関節軸の数。歩行用モデルは36、操作用は48、全身は85 |
| 冗長(redundant) | 動かしたい自由度より筋肉の数がずっと多い状態。「正解の筋肉の組合せ」が無数にあり探索が難しい |
| 筋シナジー(muscle synergy) | 100本の筋肉を、少数(K本)の「まとめて動くパターン」に圧縮した表現。人間の脳も筋肉をこう束ねるとされる |
| 閉ループ制御(closed-loop) | 体の状態(傾き・速度・接地)を**見ながら**筋肉を調整する制御。見ずに決め打ちが開ループ(open-loop) |
| 倒立振子(inverted pendulum) | 逆さに立てた棒。放っておけば倒れる。二足立ちの本質はこれを絶えず立て直すこと |
| CMA-ES(進化戦略) | 解の集団を変異・選抜して良くする最適化。今回は制御方策の数百〜千個の数値を進化させる |
| ベースライン(baseline) | 学習前・無制御の対照。「学習でどれだけ良くなったか」を測る出発点 |
| RTF(real-time factor) | シミュがどれだけ実時間より速いか。13×なら1秒の物理を約0.08秒で計算(CPU・並列度に強く依存) |
| `qpos` | モデルの**全関節の位置を一列に並べた配列**。後半の肝。関節を足すとこの並びがずれる |
| keyframe(キーフレーム) | 「実験開始時の姿勢」を `qpos` の**並び順そのまま**で書いた初期化データ。**位置(番号)で決まる**のがミソ |
| warm-start(温かい初期化) | 学習を「ゼロから」でなく「既にできる方策」から始めること |
| モーションキャプチャ(mocap) | 人の動きを記録した関節角の時系列。ここでは無料の BVH ファイルを使う |
| リターゲット(retargeting) | ある骨格の動きを、**体型も関節構造も違う別の骨格**へ移し替えること |
| IK(逆運動学 / Inverse Kinematics) | 「手先をここに置きたい」から**関節角を逆算**する計算 |
| キネマティック再生(kinematic) | 物理(力・筋肉)を回さず、関節角を直接セットして絵にすること。動きの見た目だけを作る |
| equality constraint(等式拘束) | 「この関節はあの関節の関数で決まる」という連動ルール。膝や肩に大量に入っている(後述の罠) |

# 第 I 部 —— 700筋の骨格を、自宅の CPU で立たせ・掴ませ・運ばせる

## 2. なぜ「全身骨格」で、なぜ先に調べたか

新しいことを始める前に、まず調べる。これは私の習慣だ。今回の題材は **MS-Human-700**——中国 LNS Group が作り、**ICRA 2024** で発表した全身の筋骨格モデル(Zuo, He, Shao, Sui, *Self model for embodied intelligence*)。Apache-2.0 で公開され、MuJoCo の公式モデル集 **Menagerie** にも収録されている。骨・腱・**700本の筋肉**が入った、文字通りの「全身骨格」だ。

そして論文を読んで、正直に期待値を調整した。この論文の主眼は「700筋という高次元を**階層的な低次元表現(≒筋シナジー)**で制御し、歩行を学習する」ことにある。つまり**まともに動かすには素朴な方法では足りない**と、作者自身が言っている。

> 教訓の先取り: 「筋肉で人体を立たせる」は、GPU クラスタと階層強化学習を投じても難しい、れっきとした研究課題だ。それをノート PC の CPU と進化戦略でやろうというのだから、**負ける可能性を最初から勘定に入れる**。負けたら負けたと書く——それがこのシリーズの背骨だ。

私が価値を置くのは「立たせられた」という結果そのものではない。**同じ物差しで、どこまで行けてどこで止まったかを正直に帰属すること**——それが今日書きたいことだ。

## 3. 舞台: 700筋の人体を、自宅の CPU に載せる

まず MS-Human-700 を、自作の研究基盤 onocollo(MuJoCo の上に被せた型付きランタイム)にロードした。3つの変種がある。

| 変種 | 自由度 | 筋肉 | 用途 |
|---|---|---|---|
| 全身(full) | 85 | **700** | 全身すべての筋 |
| 歩行用(locomotion) | 36 | 100 | 上半身を簡略化。立位・歩行の実験に使う |
| 操作用(manipulation) | 48 | 81 | 右腕と**詳細な手**+机上の水ボトル |

大事な事実をいくつか。

- **アクチュエータは全部「筋肉」**。ロボットのモーターのように「+3 N·mから−3 N·m」と両方向に回せるのではなく、筋肉は**縮む(引く)方向にしか力を出せない**。活性値は0〜1で、Hill 型という力‐長さ‐速度依存の非線形モデルで力が決まる。だから「関節を右に回したければ右の筋、左は左の筋」と**対で用意**し、しかも数が自由度より多い(=冗長)。
- **膝が生体力学的に精密**。単純な蝶番ではなく、大腿骨と脛骨が転がり滑る動きを、複数の補助関節と拘束式で再現している。
- 骨盤は「浮遊基底(floating base)」——地面に固定されず、3方向のスライドと3方向の回転で自由に動く。初期姿勢では高さ0.95mで直立している。
- **速度**: このモデルはノート PC(Intel Core, Ice Lake 世代のモバイル CPU)の**1スレッド・アイドル時**で **RTF 約13倍**(6秒の物理を約0.46秒、~6500ステップ/秒。dt=0.002s)。ただしこれは占有時の値で、**進化のために7コアを並列で回すと1プロセスあたり ~3〜5倍まで落ちる**(コアの奪い合い)。RTF は CPU 型番・並列度・積分器の設定でこれだけ変わるので、数字は必ず条件とセットで読むこと。それでも「何千回もロールアウトする」進化が現実的に回る速さではある。

![MS-Human-700 歩行用変種の初期直立姿勢。脚に赤く見えるのが筋肉と腱。骨盤の高さ0.95mで立っている](https://raw.githubusercontent.com/furuse-kazufumi/fullsense/main/docs/articles/assets/musculo/locomotion_init.png?v=1)

## 4. まず正直なベースライン——そして既存コントローラが「壊れる」

新しい制御を作る前に、必ず**無学習のベースライン**を測る。異常に良い数字を後で疑えるように、出発点を先に釘で打っておく。歩行用モデル(床あり)で、6秒間ロールアウトして「骨盤が0.6mを割ったら転倒」とした。

| 制御 | 転倒までの時間 | 結末 |
|---|---|---|
| 無制御(全筋弛緩) | **0.50秒** | 崩落 |
| 全筋最大収縮 | 0.99秒 | 崩落 |
| 毎ステップ乱数 | 1.00秒 | 崩落 |

**何もしなければ、人体骨格は約1秒で崩れ落ちる**。全部の筋肉を最大で固めると、剛性が上がってほんの少し延命するが、それでも立ってはいられない。これが立位課題のスタート地点だ。

そしてここで、**既存の道具が壊れることを実測した**——これが今回いちばん技術的に面白い発見だった。onocollo には既に「Menagerie のロボットの制御を進化させる」コントローラがある。だがそれは各アクチュエータに**担当関節の角度**を読ませて動かす設計だった。ところが筋肉には「担当する単一の関節」が無い(腱を介して複数関節をまたぐ)。結果、**100本の筋肉すべてが同じ(ゼロの)入力を受け取り、しかも重みを共有しているので、全100筋がまったく同じ活性を出す**。

100本の筋肉が毎瞬間まったく同じ強さで縮む——これでは二足立ちなど絶対にできない。**この退化を数値で確認した(ユニークな活性値の種類 = 1)**。だから、筋肉モデルには「全身の状態を見て、筋肉ごとに違う指令を出す」新しい表現が要る。論文の言う「階層的低次元表現」と、必要性がぴたりと一致した。

## 5. 立位タスク: 筋シナジー × 進化 —— そして正直に転ぶ

作った制御はこうだ。

1. **全身の proprioception(自己受容感覚)を読む**: 骨盤の高さの誤差・傾き(前後/左右/ひねり)とその角速度・骨盤の並進速度・左右足の接地——バランスに効く14個の量。
2. **筋シナジーに落とす**: その状態を、**K本の「まとめて動くパターン」**に線形写像し(`tanh`)、それを `K×100` の行列で100本の筋活性に展開する(`sigmoid` で0〜1に)。K=6なら方策の数値は約790個。これが論文の「低次元表現」に対応する私なりの実装だ。
3. **CMA-ES で進化**: この数値を進化戦略で最適化する。報酬は「立っている間、高さが目標に近く・上体がまっすぐ・骨盤の速度が小さいほど高得点、転んだら終了」。

> 正直な設計の訂正: 最初の報酬は「高さが目標に近ければ加点」だけだった。すると進化は狡くなり、**『ゆっくり優雅に倒れる』方策**で点を稼いだ(倒れる途中も高さはそこそこ高いから)。見た目は立っていない。そこで**骨盤の速度にペナルティ**を足し、「静かに立ち止まる」方が「ゆっくり倒れる」より高得点になるよう直した。狡さを封じる物差しの調整だ。

計算を無駄なく回すため、**モデルを1回だけ読み込んで7コアで並列評価**する仕組みも書いた(モデル読込は約2秒、1ロールアウトは数百ミリ秒なので、毎回読み直すと読込が支配的になる)。ワーカーごとに1回だけ読ませて使い回すことで、並列度ぶんの高速化が効く。

結果は——**正直に、届かなかった**。最良値(best)だけを載せると「山を代表値に見せる」ことになるので、典型値(進化後半の世代ベストの中央値)も併記する。まず**単一の乱数種**での結果はこうだった:

| 制御(単一種) | 方策の数値 | 典型(中央値) | 最良(best) | 結末 |
|---|---|---|---|---|
| ベースライン(無制御) | 0 | — | 0.5〜1.0秒 | 崩落 |
| 静的な筋緊張(定数) | 100 | ~2秒 | 3.02秒 | 最後は転倒 |
| 筋シナジー(閉ループ) | 790〜1020 | ~2.5秒 | 3.71秒 | 最後は転倒 |
| 筋シナジー+記憶(積分項) | 808 | ~3.0秒 | 4.53秒 | 最後は転倒 |

この表を見て、私は一瞬こう思った——「**記憶(積分項)を足したら 3.71 → 4.53秒に伸びた。仮説どおり、バランスには誤差の積分が要るのだ**」と。バランス制御は理屈上それが定石(積分制御)だから、話としても綺麗だった。

### n=1 に騙されかけた——乱数種を3本に増やしたら差が消えた

でも CMA-ES は確率的だ。**単一の乱数種の差は、種のアタリ/ハズレかもしれない**。そこで「記憶あり/なし」を**それぞれ3種**回して中央値を取った(公平な比較)。

| 制御 | best の中央値(3種) | best のばらつき | 典型(median-late)の中央値 |
|---|---|---|---|
| 記憶なし(plain) | **3.55秒** | 3.16〜3.80秒 | **2.71秒** |
| 記憶あり(積分項) | **3.56秒** | 3.34〜4.17秒 | **2.39秒** |

**結論は反転した**。best の中央値は 3.55 ≒ 3.56 で**ほぼ同じ**、典型に至っては記憶ありが**むしろ低い**(2.39 < 2.71)。つまり単一種で見えた 4.53秒は**同じ分布のたまたま高いスパイク**で、**記憶項が効いた証拠にはならない**。私の「記憶が効く」という綺麗な仮説は、n=3 で**支持されなかった**。

- 閉ループの制御は、崩落を **約1秒 → 典型2.5秒・最良3.5秒前後** まで遅らせた。ベースラインは明確に上回り、静的な筋緊張より閉ループの方が良い。倍率の分母は控えめに「無制御 ~1.0秒」を採る(全筋弛緩の 0.50秒 を分母にすれば数字は倍になるが、それは誇張だ)。**記憶の有無はこの範囲では有意差なし**。
- だが**6秒立ち続けることはできない**。最良の方策でも、最後のフレームは床に横たわっている。
- **教訓**: n=1 の「効いた!」は、確率的最適化ではしばしば嘘になる。綺麗な仮説ほど、複数種で median を取るまで信じてはいけない。この一件は、私が公開前に**別プロセスの fact-check**を通す運用が実際に効いた例だ(fact-check が「単一種の因果は強すぎる」と指摘 → 3種で検証 → 反転)。

![学習曲線。立てた時間は世代とともに上がるが、2〜2.7秒(スパイクで3.7〜4.5秒)で頭打ち。点線が無制御の約1秒。6秒(エピソード長)には届かない](https://raw.githubusercontent.com/furuse-kazufumi/fullsense/main/docs/articles/assets/musculo/learning_curves.png?v=1)

![最良の立位方策でも、約3.7秒後にはこの通り床へ。誇張せず「負け」を残す](https://raw.githubusercontent.com/furuse-kazufumi/fullsense/main/docs/articles/assets/musculo/stand_warm.gif?v=1)

なぜ届かないのか。素直に言えば、**線形のシナジー方策を CMA-ES で~800次元も最適化するのは、倒立振子の恒常安定化には力不足**なのだ(単純な積分の記憶を足しても、上で見たとおり救われなかった)。論文が階層強化学習を要したのと矛盾しない。ここで「立てました!」と丸めて書くのは簡単だが、実際に立ち続けてはいないのだから、そう書くのはやめておく。

## 6. 把持タスク: 舞台を変えたら、勝てた

立位が難しいのは「倒立振子」だからだ。では、**倒れる心配のない課題**なら?——操作用の変種は、肩から上が固定されていて骨盤の自由関節が無い。つまり**バランスを失いようがない**。純粋に「腕と手で何かをする」課題になる。

そこで、**81本の筋肉でできた右手に、机の上の水ボトルを掴ませて持ち上げさせた**。手は最初からボトルの約0.1m近くにあるので、本当の課題は「近づく」ことではなく——**掴んで、持ち上げて、保持する**ことだ。

同じ筋シナジー方策を、今度は「ボトルを高く持ち上げるほど加点」で進化させた。結果:

| 世代 | ボトルの持ち上げ高さ |
|---|---|
| 0(初期) | 0.006 m(=ほぼゼロ) |
| 20 | 0.39 m |
| 50(収束) | **0.825 m** |

**81本の筋肉の右手が、机の水ボトルを掴み、0.82m 持ち上げて静止・保持した**(飲む動作の前段——「口へ運ぶ」の手前まで——に相当する)。

### 正直に「放り投げ」と「すくい上げ」を疑う

高さを最大化する報酬は、**「ボトルを上に叩き飛ばす」ズルでも点が入る**。だから2段階で検証した。

これは、以前の記事で「AI 義手に箸を持たせる」話を書いたときに残った宿題——「手が無い(箸を直接動かしていた)」問題への、**本物の解剖学的な手による回答**でもある。母指・虫様筋・骨間筋まで揃った手が、筋肉の力だけで物を掴んだ。

## 7. 掴んだ先へ: 命令した場所まで運ぶ(制御可能な操作)

「掴んで持ち上げる」は、実は "どこでもいいから上へ" という一方向の課題だった。本物の操作(manipulation)は、**掴んだ物を、こちらが命令した場所へ運ぶ**ことだ。そこで方策に「目標 − ボトル」のベクトルを見せ(観測を3次元ぶん増やし)、**同じ1つの制御で、3つの違う目標**(真上/体側の飲むポーズ/前方やや上)に従えるかを試した。1つの方策が命令で運び先を変えられれば、それは「制御可能(controllable)」だと言える。

ところが素朴にやると、**またしても報酬ハッキング**に落ちた。「ボトルが目標に近いほど加点」だけにすると、**掴むことへの勾配が消える**。ボトルの初期位置がもともと近接点の底値を稼ぐので、最適化は「筋肉を弛緩させ、ボトルを机に置いたまま放置」して、動かないことで点を取った。200世代回しても、目標への最接近距離が一切改善せず凍結していた——**点数は上がるのに、掴んでも運んでもいない**。§5 の「ゆっくり倒れる」欺瞞の兄弟だ。

直し方は2つ:

- **warm-start(温かいスタート)**: §6 の検証済み把持方策を初期値にする。観測の次元が違う(把持19 → 運搬22)ので、増えた命令ベクトルの入力重みをゼロで埋め、**初期は把持方策とまったく同一**にする。すると進化の仕事は「動く把持の上に、命令追従だけ足す」ことになり、"放置" の窪地を最初から飛び越える。
- **把持維持の加点 + 終端ゲート**: 手とボトルの近さを加点し、終端ボーナスは**掴み続けている時だけ有効**にする(落とす/放り投げると0点)。

## 8. なぜ一方は負けて、一方は勝てたのか

同じモデル・同じ制御表現・同じ最適化なのに、立位は負けて把持は勝った。**決定的な違いは課題の物理的な安定性**だと考えている。

- **立位は不安定平衡**。倒立振子は、ほんの少しの傾きが指数的に増える。制御は「絶えず・素早く・正しく」立て直し続けねばならず、少しでも間違えば発散して倒れる。記憶なしの線形方策には荷が重い。
- **把持は(この設定では)安定**。肩が固定され、目標(高く持ち上げる)は一度達すれば維持しやすい。多少の制御の粗さは致命的にならない。

ただし、安定性が**唯一の**違いだと言い切るのは正直でない。少なくとも3つの交絡がある: **①リーチが既に解けている**(把持は手が最初からボトルの 0.1m 近くにある)、**②報酬の素直さ**(把持は「高いほど良い」の単調で密な報酬 / 立位は生存時間ベースで『ゆっくり倒れる』欺瞞が起きた)、**③自由度の差**(把持は肩固定で、立位を殺している不安定な浮遊基底6自由度が無い)。**主因は安定性だが、これらも効いている**——きれいすぎる物語は単一原因を過大に見せる。

そして §7 の運搬(place)は、この見立ての**3つ目のデータ点**だ。舞台は把持と同じ安定な操作変種(倒れない)なのに、そこへ「命令通りの場所へ運ぶ」という制御性の要求を足した途端、完全勝ち(把持)から**部分的勝ち(3分の1)**へ落ちた。難度は、課題の安定性だけでなく、**要求する制御の"賢さ"**でも上がる。

収穫はこうまとめられる: **「AI にできること/できないこと」は、方策の賢さだけでなく、課題そのものの安定性(と、足場・報酬・自由度・要求される制御性)で決まる**。同じ道具でも、土俵を選べば勝て、選ばなければ正直に転ぶ。そして3つの課題すべてで、**"点は上がるのに中身が伴わない" 欺瞞(ゆっくり倒れる/ボトルを放置する)を、公開前に一発の確認で潰した**——それがこの記事の一貫した作法だ。

## 9. 発端: 「口に入っていない」の一言

第 I 部のあと、私は目標点を「実際の口」に置き直したら**同じ制御の容量のまま口元まで届いた**、と判定した。数字上は届いていた(ボトル中心と目標点の距離が数センチ)。「飲む動作ができた」と書きかけた。

ところが、レンダリングした動画を見た人間(私に方向性を指示する側)から、**3つの棄却**が返ってきた。

1. **「口に入っていない」**——ボトルは喉・鎖骨のあたりで止まっていて、実際の顎(あご)には届いていない。
2. **「口も開いていない」**——そもそも口が閉じたまま。飲んでいるように見えない。
3. **「何をしているのか分からない」**——正面カメラ1つでは、腕の動きが読み取れない。

これは、このシリーズがずっと守っている作法——**「異常に良い結果が出たら、勝った気になる前に内訳を疑う」**——が、他人の目によって作動した瞬間だった。私は「距離が数センチ」という**数字を信じて、絵を疑わなかった**。人間は絵を見て、数字の嘘を見抜いた。正直に、主張を取り下げるところから始める。

## 10. 一つ目の訂正: 目標が「喉」の高さだった

まず (1) から。私が「口」として設定していた目標点は `(0.07, 0, 1.46)` だった。だが実際の顎のジオメトリを測ると、下顎の底は高さ **1.50m**、唇のあたりは **1.55m** 付近にある。私の目標 `1.46` は**顎の底より下、つまり喉・鎖骨の高さ**だった。

ボトルは「口元」でなく「喉元」に運ばれて、そこで止まっていた。距離の数字が小さかったのは、間違った目標にはちゃんと届いていたからだ——**目標の置き場所が間違っていれば、達成率が高いほど質が悪い**。目標を実際の唇の高さ `(0.05, 0, 1.55)` に直した。

これは第 I 部 §7 で私が書いた「単一の線形シナジーには、腕を体側へ引き戻す容量が足りない(だから届かない)」という説明への、自分自身への訂正でもある。**届かなかった真因は容量ではなく、目標の置き間違いだった**。容量のせいにするのは、いつでも一番ラクな逃げ道だ。ただし誤解のないように——ここで覆るのは「口に届かない原因が容量だ」という誤帰属だけで、§7 で見た「任意の一点へ厳密に置く精度は3分の1」という単一線形シナジーの容量限界そのものは、今も生きている。

> 教訓の先取り: 「アルゴリズムの限界だ」と結論する前に、**採点表(目標・報酬)が正しいかを疑え**。停滞の原因を能力に帰属するのは、たいてい早すぎる。

## 11. でも、このモデルには口が無い

次に (2)「口が開いていない」。これは私の設定ミスではなく、**モデルそのものの限界**だった。操作用変種は、腕と手をとことん精密に作る代わりに、**頭部を単一の剛体**として扱っている。顎関節も、顔面の筋肉も無い。81本の筋肉は全て腕・手・体幹のもので、**口を開ける手段が一つも無い**。

指示は明快だった——「**顎を開くモデルに改造する**」。そこで、元モデル(251MBのアセット群)をまるごとコピーして不変のまま置き、その操作用の胴体定義ファイルだけを編集して、頭部の顎ジオメトリを**独立した子ボディ `mandible`(下顎)+ヒンジ関節 `jaw_open`** として切り出した。この関節に角度を与えれば下顎が降りて口が開く。

ただし、ここには最初から**正直な線引き**がある。**この顎には筋肉が付いていない**。だから顎の開閉は、筋肉で解く動きではなく、**位置を直接書き込む台本(kinematic)**だ。**腕の把持と運搬は 81 本の筋肉が本当に解いているが、口が開くのは演出**——この区別は最後まで持ち歩く。

改造したモデルは無事に読み込めた。関節が1本増えて自由度は 48 → 49。筋肉の数(81)は変わらないので、**学習済みの制御はそのまま載るはず**だった。顎を閉じた絵・開いた絵も個別に確認して、開閉そのものは動いた。——ところが、そこに学習済みの飲む制御を載せた瞬間、話がおかしくなる。

## 14. 真犯人: keyframe は「番号」で決まる。関節を足せば、全部ずれる

なぜボトルだけ、しかも高さ 1.57m ぶんも落ちたのか。ここが、MuJoCo(に限らず物理エンジン)を触る人全員に効く教訓だ。

MuJoCo は、モデルの**全関節の位置を一列の配列 `qpos` に詰める**。各関節は、体の木構造の順に `qpos` の「何番目から何番目」という**場所(スロット)**を割り当てられる。そして「実験開始時の姿勢」を定義する **keyframe** は、その `qpos` を**値の並びそのまま**で書いた、ただの数の列だ——`qpos="-0.07 0.03 ... 0.94 ..."` のように。**i 番目の値は i 番目のスロットに入る**。位置で決まる。

さて、私は顎ヒンジ `jaw_open` を頭部に足した。MuJoCo はそれに **42番目のスロット**を割り当てた。すると——**42番以降の関節は、全部1つずつ後ろにずれる**。ボトルの位置を保持するスロットも、42→43 へ動いた。ところが、**keyframe の数の列は 48 個のまま**、元モデルの並びを引きずっていた(顎を足したのに、開始姿勢の数列を更新していなかった)。モデルの `qpos` は 49 個に増えたのに、keyframe は 48 個。MuJoCo は足りない1個を末尾に 0 で埋める。結果、**42番目から先が、全部1つずつズレて読まれた**。

図にするとこうだ。

```
スロット番号:  ... 41    42(新)   43       44       45      46      47      48
本来の中身:    ... 腕末  [顎=0]   ボトルx   ボトルy   ボトルz   回転…    回転…    回転…
keyframe実際:  ... 腕末   0        0        0        -1.57    0.32    0       0(padding)
                          ↑ここから全部1つ手前の値を読んでいる
```

腕(スロット41以前)は無傷だった——**ずれは42番目から始まったから**。だがボトルは違う。ここで一つ、大事な前提を挟む: **このボトルは「机の高さ(0.94m)を原点にした上下スライド関節」に乗っていて、keyframe に入る値はその原点からの相対変位(メートル)を表す**。本来ボトルの上下スライドは 0(=机の上にそのまま)であるべきだった。

ところが1つずれた結果、その高さ欄に、**本来は隣の関節の回転角だった `-1.57` という値**が流れ込んだ。−1.57 は**ラジアンで測った回転角(約 −90 度)**のつもりの数字だ。それが**そのまま垂直スライドの変位(−1.57 メートル)として読まれた**——角度の数字が、距離の数字に化けたのだ。だからボトルは机の高さから 1.57m ぶん沈み、**0.94 − 1.57 ≒ −0.63m、床を突き抜けた地中**に現れた。

「0.94 − 1.57 = −0.63」が引き算ではなく足し算(相対変位の加算)になるのは、ボトルの高さが**絶対座標ではなく机からのスライド量**だからだ——ここを飛ばすと「z が丸ごと −1.57 に上書きされるはずでは?この一致は出来すぎでは?」と疑われる。実際、この記事の内訳を検証してくれた別プロセスも、モデル定義(ボトルが上下スライド関節に乗っていること)を一次ソースで確かめるまで、一度は「破綻している」と判定しかけた。**キレイに合う数字ほど、機構まで遡って確かめる**——それはこのシリーズの信条そのものだ。

**関節を1本足すことは、keyframe の全スロットを1つずらすこと**なのに、私は数列を古いまま放置していた。緑のテストは通っていた(モデルは読み込めるし、関節数も筋肉数も正しい)。**テストが検出できない、位置ずれという静かなバグ**だ。そしてそれを暴いたのは、テストではなく——**動画を見た人間の「口に入っていない」の一言**だった。

## 15. 直す: 0 を一つ、正しい場所に

原因が分かれば、直し方は拍子抜けするほど簡単だ。**元の 48 個の keyframe に、顎のスロット(42番目)へ `0`(顎は閉じた状態=角度0)を1個挿し込んで、49 個にする**。そうすれば、42番以降は本来のスロットへ正しくずれ、ボトルは机の上に戻る。

```
変更前(48個): ... 0.3141  0 0 0  -1.57 0.32 0
変更後(49個): ... 0.3141  0 0 0 0  -1.57 0.32 0
                          ↑ 顎の 0 を1個挿入
```

適用して測り直すと、顎モデルは**元モデルと数値まで一致**した。

| 測った量 | 元モデル | 顎モデル(修正後) |
|---|---|---|
| ボトル開始 z | 0.94 m | **0.94 m** |
| 持ち上げ量 | +0.62m(z=1.56へ) | **+0.62m(z=1.56へ)** |
| 掴み続けた?(手〜ボトル) | ✓ (0.043m) | **✓ (0.043m)** |
| 口(唇)への最終距離 | 0.050m | **0.048m** |

手〜ボトルの相対位置ベクトルの差は **0.0(測定精度 1e-6 未満で一致)**——つまり顎モデルは、把持と運搬に関して元モデルと**区別がつかない**動きを再現した。学習し直しは一切要らなかった。壊れていたのは制御ではなく、初期化データの並びだったのだから。

## 16. 飲んだ

修理が済んで、ようやく本来やりたかった絵になる。台の上のボトルへ手を伸ばし、掴み、口元へ運び、そこで顎が開く。

> 何を持ち帰るか(第 II 部の教訓、3つ): **① 停滞や失敗の原因を「能力の限界」に帰属する前に、採点表(目標・データ)を疑え** —— 「口に届かないのは容量不足」は「目標を喉の高さに置いていたから」だった。**② 推測でコードを直す前に、測って犯人を特定せよ** —— 「腕がずれた」は測ったら外れで、真犯人はボトルの初期位置だった。**③ keyframe や初期化データは「番号(位置)」で決まる。構造(関節)を足したら必ず作り直せ** —— 位置ベースの初期化を更新し忘れると、テストは緑のまま物体だけが静かに床へ落ちる。そしてその静かなバグを暴いたのは、テストではなく絵を見た人間の違和感だった。**人間をループに残す(Human-in-the-Loop)**とは、こういう瞬間のためにある。

# 第 III 部 —— evis: この骨格がマスコットになって、踊り・箸で食べた

> ここから先は、上で「立たせようとして正直に転んだ」あの 700 本の筋肉の骨格を、**マスコット化して mocap で動かした**記録。主役はまたしても成功談ではなく、**「歩かせたら老人みたいな猫背になった」その真犯人を推測でなく測定で捕まえた過程**です。

honest な但し書きを先に: 第 III 部は**キネマティック再生**(各フレームの関節角を直接与える)であって、筋肉で駆動しているわけではない。箸も「持っている風」の剛体プロップで、指で握ってはいない。**どこが本物でどこが演出か**は最後に明記する。

## 17. 出発点 — evis という「中身が見える人体」

evis の素体は、第 I 部と同じ **MS-Human-700**。全身 85 自由度・**700本の筋肉**を持つ、生体力学研究用の人体モデルだ。皮膚がなく、骨(白)と筋・腱(赤)がむき出しになっている。この「肉を剥いだ姿」が、そのままキャラクターの魅力になった。名前は **evis** に決めた。由来は二層で、

- **恵比寿(えびす)** — 七福神のひとり。縁起がいい。
- **eviscerate** — 内臓・肉を取り除くこと。まさに骨と筋だけになった evis の姿そのもの。

house style は「白い骨 + 暗いスタジオ + 発火するように光る赤い筋 + コミカルな白目」。筋の光り方には仕掛けがあって、キネマティック再生では筋活性がないので、**各部位の"速さ"で赤く発火させている**——速く振った腕がパッと光る。動きが要求する運動パターンが可視化される、というわけだ。

## 18. なぜ mocap か、そして最初の壁は「技術」ではなく「ライセンス」だった

手作りのサイン波で腕を振らせても、動きが硬い。**本物の mocap を移植したい。** ところが最初にぶつかったのは技術ではなく**ライセンス**だった。evis を含む FullSense は商用 dual-license なので、mocap データも商用利用できる必要がある。有名どころを調べると:

| ソース | 形式 | 商用 | SMPL 依存 | 判定 |
|--------|------|------|-----------|------|
| **CMU MoCap**(cgspeed BVH 変換) | BVH | **可** | なし | **採用** |
| AMASS / AIST++ | SMPL パラメータ | 不可 | **要 SMPL(非商用)** | 除外 |
| Mixamo | FBX | 製品内は可 | なし | 要アカウント・データ再配布不可 |
| Bandai-Namco / LaFAN1 | BVH | **不可(NC)** | なし | 除外 |

`SMPL` は人体メッシュの標準モデルだが**研究用(非商用)**ライセンスで、AMASS も AIST++ もこれに依存する。よく使われるが、商用製品には持ち込めない。答えは **CMU Graphics Lab Motion Capture Database** だった。ライセンス文は "This data is free for use in **research and commercial** projects worldwide"。BVH で自己完結(SMPL 不要)、git で自動取得できる。ただし一点 caveat があって、**「データそのものを(変換形でも)再販してはいけない」**。だから「リターゲット済みのアニメ」を配るのは OK だが、**BVH ファイルそのものはリポジトリに同梱しない**(必要なとき取得スクリプトで落とす)ようにした。

> 教訓: 「技術的に最良」と「配れる」は別。研究デモが商用製品に化けるなら、**最初にライセンスを敵対的に裏取り**したほうがいい。

## 19. リターゲットの仕組み — 「回転」ではなく「位置」を移す

BVH の骨格(標準的な人型)と MS-Human-700 は、関節の構造がまるで違う。MS-Human-700 は OpenSim 由来で、たとえば骨盤ルートが quaternion の自由関節ではなく**6個の独立した1自由度関節**、肩は「幽霊ボディ」を挟んだ複雑な肩帯になっている。回転角をそのまま移すのは地獄だ。

そこで**位置ベース**にした。BVH を forward kinematics で解いて、**各関節の"世界座標(点群)"だけ**を取り出す。回転は一切移さない。あとは、その点群に evis の対応する体の部位が重なるように、**差分 IK(Levenberg-Marquardt)**で関節角を解く。手・肘・膝・足・頭など約 16 点を狙い、前フレームから温めて解くので 1 フレーム約 30ms、5 秒のクリップが数秒でリターゲットできる。回転を移さないので、あの厄介な肩帯も IK が勝手に良い形に配分してくれる。

**ここに一つ、キネマティック特有の罠があった。** MS-Human-700 には膝・肩帯・手首に **42 個の等式拘束**(「この幽霊関節は肩の角度の多項式で決まる」)が入っている。ところが**関節角を直接セットする再生では、この拘束が MuJoCo に強制されない**。放っておくと IK が肩甲骨の幽霊ボディをあらぬ方向にねじり、肩が壊れる。なので毎フレーム、**多項式を自分で評価して従属関節を書き込んで**やる。これで膝の screw-home も肩のリズムも正しく動く。(——お気づきの通り、第 II 部の keyframe バグと同じ「位置で決まるデータは自分で面倒を見る」という主題が、ここでも別の顔で出てくる。)

## 20. 本題 — 「腰が老人みたいに曲がる」その真犯人を、測って捕まえる

歩かせてみた。動く。……が、レビューしてもらうと一言、**「腰の曲がり方が老人みたいだ」**。側面から見ると確かに、頭が前に突き出て背中が丸い、典型的な"猫背"だった。ここからが本章の主役、**推測でなく測定で真犯人を追い詰める過程**だ。

**仮説1: 頭が前に出ている?** 頭と骨盤の前後差を測ると **0.3cm**。ほぼ真上。**却下。**

**仮説2: mocap 元がそもそも猫背?** 元 BVH の首の前傾を測ると **9.5°**(軽い)、胴体は 1.6°。ほぼ直立。**元データは猫背ではない。リターゲットが増幅している。**

**仮説3: 姿勢正則化が弱い?** 脊椎・首を中立へ弱く引く項を足したが、**視覚的にほぼ変わらない**。マーカーの引く力に負けている。

推測をやめて、**関節角を1個ずつ実測した**。すると犯人が現れた:

```
T12_L1_FE      = -28.6°   (可動域 [-29, +29] → 負の限界に張り付き)
T1_head_neck_FE = +28.6°  (可動域 [-29, +29] → 正の限界に張り付き)
```

中背(胸腰椎)が片方の限界へ、首が反対の限界へ、**両方が飽和**していた。これが猫背の正体。ではなぜ IK は関節を限界まで曲げたのか。

**真犯人はマーカーの高さの取り違えだった。** evis の `thoracic1`(胸椎最上部)は骨盤の **0.50m 上**(肩の高さ)にある。ところが私はそこに、BVH の `Spine1`(骨盤の **0.26m 上**=中背)を割り当てていた。**肩の高さの体を、中背の高さへ引き下げようとして、3 セグメントしかない脊椎が圧縮され、関節が限界まで折れ曲がっていた**のだ。

修正はシンプルだった。**高さの合う対応に変える**——`thoracic12`(0.23m 上)←`Spine1`(0.26m)。過剰に拘束していた `thoracic1`/`lumbar5`/頭頂マーカーを外し、姿勢正則化を少し効かせる。結果、歩行は直立になり、しかも**ダンスの表現的な背屈(前屈・のけぞり)は残った**——あれはマーカーが本当に要求している動きだからだ。

> 教訓(第 III 部で一番言いたいこと): **「たぶん頭が前に出ている」で直そうとすると外す。** 採点の内訳(関節角)を測ると、犯人は思いもよらない「マーカーの高さ」だった。第 II 部の「まず測る」と、まったく同じ精神だ——**推測する前に測れ。**

## 21. 目を 3D にしたら、小細工が全部消えた

evis の表情(＞＜ や ◎◎)は、最初は **2D の描き込み**だった。頭の 3D 位置をカメラに投影して画面上の目の座標を求め、深度バッファで「今この目は見えているか(横を向いて骨に隠れていないか)」を判定して、白目と顔文字を上から貼る……という仕組み。動くには動いたが、**横顔のとき遠い方の目が背景に投影されて宙に浮く**バグが残った。

そこへ一言、**「白目を 3D の球としてモデルに一体化して、眼球に直接テクスチャで表情を描けば?」** これが正解だった。表情ごとに**キューブテクスチャ**(前面に顔文字、他は白い強膜)を焼いた眼球の球を頭に埋め込み、感情ごとに用意しておいて、**表示する 1 組だけ残して他を透明にする**ことで挿げ替える。すると:

- 目が**頭と一緒に回転**する。
- **骨(頭蓋)が自然に目を隠す**——後頭部を向けば目は消える。深度判定も投影計算も要らない。
- どの角度でも正しい。ダンスで頭が回っても、転倒で下を向いても勝手に正しくなる。

投影+深度の 2D 小細工が丸ごと(約 80 行)消えた。感情は 8 種(neutral の丸目 ●●、joy ＞＜、surprise ◎◎、love ♥♥ はカラー絵文字テクスチャ、dead ×× ……)+ 任意の文字。ちなみに全角の ＞＜ が絵文字と誤判定されて薄く描かれるバグもここで直した(判定範囲の取り違え)。

# 第 IV 部 —— 全体の正直な限界と、次へ

## 23. どこが本物で、どこが演出か(統合版)

honest disclosure がこのシリーズの核なので、記事全体の境界を1か所に集めて明示する。

- **本物(研究層・筋駆動)**: 第 I 部の立位・把持・運搬、第 II 部の飲む動作の**腕の把持と運搬**は、81(または100)本の筋肉を進化計算で学習させた**閉ループの筋駆動**。IK・force-closure・keyframe パリティの検証も本物。立位の「負け」も、n=3 で反証した「記憶の効果なし」も、誇張せず残した実測だ。
- **演出(キャラクター層)**: 第 II 部の**顎の開閉**は kinematic(顔面筋非搭載ゆえの台本)で、しかも設計可動域(+0.05 rad)を超える +0.6 rad まで qpos 直書きして開けている——物理を無視した演出だと明記する。第 III 部の evis の踊り・走り・箸は**キネマティック再生**で、筋の赤い発火は「速さ」の proxy(筋活性ではない)、目・アホ毛はリグ、箸は**剛体のプロップ**(指で握ってはいない)。
- **「飲む」そのものはしていない**。液体の摂取をシミュレートしているのではなく、ボトルを開いた口元へ運ぶ所作だ。飲む「ジェスチャ」であって、飲む「生理」ではない。
- **省略**: 胸郭の**肋軟骨**は骨のみモデルなので省略されている(前面がスカスカに見える正体)。解剖図で正しい形(肋骨 1–7 は胸骨へ、8–10 は肋骨弓を作る)まで裏取りしたが、キャラクター向けの近似としては難しく、既定でオフにした。

要するに: **筋肉が本当に駆動しているのは「立つ(ただし正直に負け)・掴む・運ぶ・飲む腕」まで**。「口を開く」「踊る」「箸を握る」は、その上に乗せた見た目の層だ。この線を曖昧にしたまま GIF を見せると誇張になるので、太字で残す。

## 24. 次回へ

三つの山を越えて、evis は「立とうとして正直に転び・掴み・運び・飲み・踊り・箸で食べる」までできた。だが残した宿題は明確だ。

- **箸を"本当に指で握る"**のは、キネマティックの延長ではなく、**筋肉を進化で学習させる**別の山だ。81 本の筋肉の手が、剛体プロップではなく本物の箸を摘まみ、食べ物を口へ運べるか。
- **立位の負けを取り返す**。単純な積分の記憶では駄目だったので、次は再帰(recurrent)方策か、明示的な足首/腰の戦略か、階層を試す。
- **評価(eval)そのものに顔をつける**。今回 evis の表情を転倒に配線したように、歩行の学習でコケたら ×× になり、うまく進めば ＞＜ で笑う——**シミュレーションが自分で実況する**マスコットへ。

> 測って、正直に負けを残して、次に登る。良い結果が出たときほど内訳を疑い、詰まったら推測でなく測る——それが、私がこのシリーズで守っている一点だ。骨と筋だけの evis の物語は、まだ続く。

## 付録: 方法(再現用メモ)

数字を条件抜きで出すのは不誠実なので、前提を並べておく。

- **モデル**: MS-Human-700(Apache-2.0)/ MuJoCo 3.10 / 積分ステップ dt=0.002s。全身85 DoF・700筋、歩行用36 DoF・100筋、操作用48 DoF・81筋の3変種。
- **CPU**: Intel Core(Ice Lake 世代モバイル)、8コア。進化評価は**7ワーカー並列**、単発計測は**1スレッド・アイドル**。
- **立位**: 歩行用シーン(床あり)、エピソード6秒、転倒閾値=骨盤高さ0.6m(初期0.95m)。CMA-ES、pop 16〜40、世代60〜250。方策は筋シナジー(K=6 or 8)。記憶あり/なしの比較はそれぞれ乱数種3本で中央値を取り、単一種の見かけの差(4.53秒)が消えることを確認した。
- **把持**: 操作用シーン(肩固定)、エピソード3秒、CMA-ES pop 28・K=8・250世代のうち gen50 で最良。接触摩擦 μ=1.0。
- **運搬(place)**: 同じ操作用シーン、目標3点(真上/体側/前方やや上)の平均で採点。観測=把持19次元+命令ベクトル3次元。把持 champion から warm-start(命令入力の重みをゼロ埋め)、sigma0=0.25。gen30-50 で fitness ~1021 に収束。
- **飲む(顎モデル)**: 操作用変種の頭部顎ジオメトリを子ボディ `mandible` + ヒンジ `jaw_open`(軸 z、設計可動域 −0.7〜0.05 rad)に分離した派生モデル。自由度 48→49、筋肉 81 は不変。描画時の顎開けは設計可動域を超える +0.6 rad まで qpos 直書き(リミット非適用)で、これは演出。バグ=顎ヒンジは `qpos` の42番目に入り以降のスロットを1つずらす。keyframe が48個のまま zero-pad→ボトルの上下スライド欄(机 0.94m からの相対変位)に回転角 −1.57 が入り z=0.94−1.57=−0.63m に落下。修正=元の48個 keyframe の42番目に `0.0` を挿入し49個に。

```python
import numpy as np
# orig_key48 = 元モデルの keyframe(48 値)
broken = np.concatenate([orig_key48, [0.0]])   # 末尾に 0 を足しただけ = MuJoCo の自動 padding 相当(壊れる)
fixed  = np.insert(orig_key48, 42, 0.0)         # 42 番目(0-index)に顎の 0 を挿入 = 正しい(49 値)
# reset 直後にボトルの世界 z を測ると:
#   broken -> z = -0.63(床下)   /   fixed -> z = 0.94(机の上)= 元モデルと一致
```

- **evis(mocap)**: mocap = CMU Graphics Lab Motion Capture Database(商用可・SMPL 非依存)。取得は `scripts/fetch_cmu_dance.py --motion`(BVH は再配布不可のため同梱せず on-demand)。位置ベース差分 IK(Levenberg-Marquardt、numpy + mujoco のみ、scipy 不要、~30ms/frame)。膝・肩帯・手首の 42 等式拘束は毎フレーム多項式を評価して従属関節へ書き込む。表情は感情ごとのキューブテクスチャ眼球を頭に埋め込み alpha で挿げ替え。
- **実装**: リターゲッタ `src/onocollo/evolve/mocap_retarget.py`、マスコット `scripts/musculo_mascot.py`、筋制御 `src/onocollo/evolve/musculo.py`。出力は mp4(h264、Qiita 埋め込み用)/ gif は拡張子で自動切替。
- **数値の来歴**: すべて `out/musculo/*.json` と保存済み方策の再実行から取得。本記事の全定量主張は、公開前に**独立の別プロセスで一次データ・実コードへ再照合(fact-check)+編集レビュー**を通した。RTF の条件明記・立位の記憶効果を n=3 で反証・把持の force-closure 検証・keyframe バグの機構確認・顎の可動域超え開示は、その指摘を受けて直したものだ。
